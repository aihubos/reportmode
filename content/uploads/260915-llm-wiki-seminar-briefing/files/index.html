01 / EXECUTIVE SUMMARY

도구 도입보다 먼저,
어떤 지식을 어떤 결과로 바꿀지 정한다.

세미나의 공통 메시지는 명확하다. 사람이 선별한 자료와 판단을 LLM Wiki에 축적하고, 이를 AI가 찾아 업무에 활용하게 한다. 성과의 기준은 저장된 문서 수가 아니라 근거 있는 결과물을 반복해서 만드는 능력이다.

지식

좋은 재료가 먼저다

업무와 관계있는 자료, 최신 정보, 수집 이유를 함께 남긴다. AI가 조직의 상황을 저절로 아는 것은 아니다.

실행

검색에서 제작으로

목차와 연결을 통해 필요한 지식을 찾고, 보고서·슬라이드·업무 답변에 활용한다. 작업 과정도 다음 업무의 재료가 된다.

운영

사람의 판단을 남긴다

목적, 핵심 논지, 완료 기준, 최종 판단은 사람이 책임진다. 자료 정리와 반복 작업부터 위임 범위를 넓힌다.

경영 판단 제안

반복되는 보고 업무 하나로 작게 시작한다. 기존 자료의 재사용 효과와 전체 소요 시간을 확인한 뒤 범위를 넓힌다. 현재 강연만으로 회사의 절감률·투자수익·전사 적용 가능성을 확정할 수는 없다.

03 / KNOWLEDGE FOUNDATION

LLM Wiki는
AI가 함께 읽고 정리하는 지식 기반이다.

브리니티는 LLM Wiki를 좋은 식재료가 손질되어 있는 냉장고에 비유한다. 사람은 재료를 고르고, AI는 정리하며, 사용자의 목적에 맞춰 필요한 재료를 꺼내 결과물을 만든다.

왜 필요한가

일반 모델이 학습한 지식만으로는 지금 진행 중인 프로젝트, 내부 판단, 개인의 관심과 맥락을 충분히 알 수 없다. 업무에 필요한 별도 자료를 제공하고, 이후에도 반복해서 찾을 수 있게 만드는 것이 출발점이다. 발표자는 이를 자신에게 가치가 높은 ‘골드 데이터’라는 표현으로 설명한다.

PDF·PPT·웹페이지를 매번 해석하는 대신 핵심 내용과 개념을 Markdown 문서로 정리하고 연결한다. Markdown은 제목과 목록 등을 간단한 기호로 표현하는 텍스트 형식이다. 원본과 정리본의 역할을 나누면 사람이 읽는 자료와 AI가 탐색하는 자료를 함께 관리할 수 있다.

저장되는 내용

  • 수집한 원문과 출처
  • 문서에서 추출한 개념·사람·조직
  • 관련 내용을 찾는 목차와 링크
  • 질문을 통해 만든 종합 메모와 결과물

그 자체로 보장되지 않는 것

  • 모든 문서를 빠짐없이 찾는 능력
  • 내용의 사실성이나 최신성
  • AI가 만든 연결의 적절성
  • 업무의 완전 자동화와 비용 절감

강연 근거: 07:48–15:40, 20:00–22:28. 효율 개선은 강연의 취지이며 이 보고서에서 측정한 결과가 아니다.

04 / HUMAN JUDGMENT

자료보다 먼저 목적을,
요약 옆에는 사람의 판단을.

1

만들 산출물을 먼저 정한다

강의, 프로젝트, 영상, 보고서 등 활용 목적을 정한 뒤 자료를 모은다. 수집 기준이 없으면 위키가 커져도 필요한 결과를 얻기 어렵다. 기업에서는 ‘무엇을 저장할까’보다 ‘어떤 의사결정을 지원할까’를 먼저 합의해야 한다.

2

왜 수집했는지 기록한다

시연에서는 사람과 에이전트의 역할 분리가 인상적이었고 이를 영상으로 만들고 싶다는 이유를 추가했다. 같은 원문이라도 활용 의도가 다르면 중요한 부분과 연결 대상이 달라진다.

3

사람의 글과 AI의 글을 구분한다

사람이 작성한 생각·판단과 AI가 생성한 정리본을 분리한다. 브리니티는 저장 공간인 볼트를 나누는 방식을 설명했다. 기업에서는 담당자가 승인한 판단과 아직 검토하지 않은 AI 초안을 구별하는 데 적용할 수 있다.

05 / KNOWLEDGE LIFECYCLE

수집 → 정리 → 탐색 → 활용 → 축적.

강연은 특정 제품의 고정된 표준 구조가 아니라 각자 목적에 맞게 조정한 작업 방식을 설명한다. 아래는 녹취에 나타난 흐름을 경영진이 이해하기 쉽게 재구성한 것이다.

01 · RAW

원문 수집

PDF, 글, 회의 자료를 원본으로 보관한다. 출처와 수집 이유를 함께 남긴다.

02 · INGEST

내용 정리

AI가 읽고 개념별 문서로 나눈다. 기존 지식의 중복·차이·연결 후보를 찾는다.

03 · INDEX

목차 갱신

문서의 설명과 연결을 갱신한다. 새 자료가 있어도 목차에 드러나지 않으면 탐색에서 빠질 수 있다.

04 · QUERY

질문과 탐색

목차를 먼저 보고 필요한 본문을 따라 읽는다. 관련 근거를 사용해 답변을 만든다.

05 · SYNTHESIS

결과 재사용

발견한 내용을 종합 메모로 저장하고 콘텐츠와 업무 결과물에 활용한다.

한 번 정리하고 끝나는 시스템이 아니다

강연에서는 끊긴 링크, 연결이 없는 페이지, 중복 자료를 정리하는 청소 기능도 소개했다. 새 정보와 기존 정보가 충돌하면 차이를 기록하는 방식도 질의응답에서 언급했다. 최신 자료를 계속 반영하지 않으면 오래된 판단이 반복될 수 있다.

운영 시사점

자료 수집 담당만 정해서는 충분하지 않다. 목차 관리, 내용 갱신, 결과물의 재사용 여부까지 업무의 일부로 정해야 한다.

검색 기술과 함께 사용할 수 있다.

07 / PART ONE DEMONSTRATION

실제 시연의 중심은
새 자료를 기존 지식과 연결하는 과정이었다.

1. 관심 있는 두 글을 수집

사람과 AI의 역할을 다룬 글들을 대상으로 웹 클리핑을 진행했다. 수집이 원활하지 않은 경우에는 원문을 복사해 넣는 방식으로 보완했다. 원문 제목과 링크는 녹취만으로 확정하기 어려워 이 보고서에 임의의 출처를 붙이지 않았다.

2. 처리 대상을 명확하게 지정

수집 폴더 전체를 한 번에 맡기지 않고 두 문서의 경로를 지정했다. 발표자는 한꺼번에 많은 자료를 처리하면 원하는 세부 내용을 놓칠 수 있다고 설명했다. AI는 기존 개념과의 중복과 연결을 파악하고, 수집 의도를 추가로 질문하도록 구성돼 있었다.

3. 개념과 목차를 갱신

하네스 엔지니어링, 개인 맥락 관리, 관련 인물 등 개념이 추출되는 과정을 설명했다. 연결 자체는 모델의 판단이므로 모델이나 실행 시점에 따라 달라질 수 있다는 점을 발표자가 직접 짚었다.

4. 위키 안에서 질문하고 발견을 저장

사람과 에이전트의 협업 역할을 질문하고, 목차에서 관련 문서를 찾아 근거를 연결하는 방식을 보여주려 했다. 시간 제약 속에서 기존 질의 예시도 함께 설명했다. 답변은 종합 메모로 저장해 이후 글이나 영상의 재료로 활용한다.

개인 지식으로 확장

논문 관리, 문서 저장소, 화면 기록, 메신저와 이메일 등의 연계를 소개했다. 개인 데이터 일부에 로컬 모델을 활용한다는 설명도 있었다.

확장에 따른 비용

관리 대상과 갱신 책임이 늘어난다. 오래된 정보가 답변에 사용될 수 있고, 에이전트와 연결 도구를 유지하는 부담도 커진다는 점을 함께 언급했다.

강연 근거: 23:23–43:14, 45분대, 50:50–57:52. 시연 설명은 녹취 기반이며 화면·파일을 독립 확인한 결과가 아니다.

08 / AGENT ORCHESTRATION

역할은 나누고,
공통 지식은 함께 쓴다.

두부재경은 LLM Wiki를 여러 에이전트가 함께 일하는 공간으로 확장했다. 여기서 오케스트레이션은 누가 어떤 일을 맡고, 어떤 자료를 보고, 다음 담당자에게 무엇을 넘길지 조정하는 일을 뜻한다.

왜 여러 역할로 나누는가

한 대화에 모든 일을 넣으면 맥락이 섞이고 하나의 관점에 의존하기 쉽다는 문제의식이다. 역할별 설정과 기억을 나누면 연구, 작성, 이미지, 일정 관리처럼 서로 다른 업무를 지속적으로 운영하기 편하다고 설명했다. 이는 발표자의 운영 경험이며 에이전트 수가 많을수록 성과가 좋아진다는 일반 법칙은 아니다.

사람 · 목적과 완료 기준을 제시
총괄 에이전트 · 업무 분해와 전달, 진행 기록
자료 조사문서 작성이미지 제작일정 관리
공유 위키 · 출처 / 개념 / 회의 기록 / 결과물
역할별 설정과 개별 기억은 구분

지속적으로 운영하는 봇과 임시 하위 에이전트

발표자는 별도 봇을 운영하면 역할과 기억을 개별적으로 축적하기 쉽고, 해당 봇이 다시 하위 에이전트에 작업을 맡길 수도 있다고 설명했다. 기업 관점에서는 반복되는 책임을 맡는 역할과 일시적인 작업 단위를 구별하는 것으로 이해할 수 있다.

Claude, Codex, Gemini 등 도구·모델 계열을 업무 특성에 맞게 섞어 쓴 사례가 소개됐다. 개별 모델명·버전과 우열에 관한 발언은 녹취 오류 가능성과 개인 평가의 성격을 고려해 구매 추천으로 옮기지 않았다.

강연 근거: 61:28–71:15. 도식은 강연 내용을 단순화한 설명이며 실제 시스템 구성도를 복제한 것이 아니다.

09 / OPERATING SYSTEM

위키는 기억을 제공하고,
규칙과 실행 장치는 일하는 방식을 정한다.

발표자가 설명한 운영 요소
요소쉬운 설명강연에서의 역할
최상위 규칙전체 팀의 공통 원칙정체성, 완료 기준, 핵심 문서 경로 등을 안내
역할별 설정각 에이전트의 업무 설명서자료 조사 등 담당 업무와 행동 원칙을 지정
페르소나역할을 알아보기 위한 말투·외형여러 봇을 운영할 때 구분을 돕는 장치로 활용
규칙 라우팅상황별로 필요한 지침을 찾아 읽기모든 규칙을 매번 읽는 부담을 줄임
훅특정 시점에 자동으로 실행되는 장치세션 시작·맥락 압축 등의 시점에 기억과 규칙을 다시 제공하는 방식 소개
개별 기억역할별 경험과 주의사항실수와 작업 특성에 따라 참고할 내용을 다르게 축적
작업대장현재 진행 중인 업무 목록SQLite 기반으로 작업 상태를 관리한다고 설명

대화 기록과 업무 기록은 역할이 다르다

후반부에서는 회의 진행과 최종 결과를 문서로 남기는 방식을 설명했다. 대화 로그만 읽는 것보다 작업 목적, 산출물, 완료 상태가 연결된 기록을 함께 보는 것이 맥락 파악에 유용하다는 입장이다. 녹취에는 완료 안내를 아직 하지 않아 결과 문서가 갱신되지 않은 예시도 등장한다.

기업에 적용할 핵심

말투나 캐릭터보다 업무 책임과 기록 연결을 먼저 정한다. ‘누가 맡았는가’, ‘어떤 자료를 사용했는가’, ‘무엇이 끝났는가’를 알아볼 수 있어야 한다. 자동 규칙의 존재만으로 실제 준수가 보장되는 것은 아니다.

강연 근거: 73:20–87:46. 훅의 제품별 개수·지원 범위는 별도로 검증하지 않아 비교 수치를 제외했다.

10 / OUTPUT PRODUCTION

위키의 가치는
다음 결과물을 만들 때 드러난다.

후반부는 전반부 자료를 위키에 저장하고 기존 지식과 연결한 뒤 슬라이드와 PDF 제작에 활용하는 흐름을 설명했다. 외부 문서뿐 아니라 실제 업무 과정에 남긴 지시와 경험도 결과물의 근거로 사용한다는 점이 특징이다.

INPUT

발주 내용 정리

목적·청중·주요 내용과 필요한 결과물을 구체화한다.

CONTEXT

세미나 자료, 기존 문서, 업무 기록을 참고한다.

BUILD

제작 업무 분담

문서와 이미지 등 제작 업무를 나누고 총괄이 진행을 관리한다.

RECORD

산출물과 경과 저장

회의 기록과 결과 문서를 연결해 이후 작업에 재사용한다.

슬라이드에서는 장별 핵심 메시지가 필요했다

두부재경은 슬라이드 제작의 자동화 범위를 개인적으로 최대 약 60% 정도로 본다고 설명했다. 매번 청중과 말하고 싶은 내용이 달라 장별로 주요 내용을 사람이 넣어야 원하는 결과를 얻는다는 이유다. 반면 어떤 화면을 캡처하고 어떤 이미지를 사용할지에 대한 맥락이 쌓이면 반복 작업 시간을 줄일 수 있다고 말했다.

문체·시각 표현·내용 구성을 별도로 살폈다

강연에서는 문체를 다듬는 역할, 이미지와 크기·배치를 살피는 역할, 장의 필요성과 논지의 정확성을 검토하는 역할을 나누는 제작 방식도 소개됐다. PDF 역시 초안을 만든 뒤 유사한 과정을 거쳐 산출한다고 설명했다. 이러한 과정의 소개만으로 최종 자료의 오류가 모두 제거됐다고 판단할 수는 없다.

강연 근거: 88:30–97:54. ‘60%’는 측정 방법·표본이 제공되지 않은 발표자의 경험적 추정이다.

주장별 판단 범위

실시간 제작일부 저장·토론을 진행했고 결과물 일부는 사전 준비전체 제작의 실시간 성공으로 표현하지 않음
슬라이드 자동화발표자 추정 최대 약 60%회사 절감 목표나 계약상 성능 기준으로 쓰지 않음

모델 성능글쓰기·지속 작업·이미지 읽기 등의 경험적 비교통제된 비교 실험이나 최신 제품 평가가 아님
조직 확장소규모 동기화, 공유 에이전트, 큰 조직의 별도 시스템 연계 제안개인 운영 사례가 전사 운영을 입증한 것은 아님

제공 텍스트는 자동 전사 오류로 보이는 용어와 혼재된 화자 표기가 포함돼 있고, 마지막 발언도 문장 중간에서 끝난다. 따라서 발언의 취지를 정리하되 불명확한 제품명·정확한 수치·확인되지 않은 링크는 보강해서 만들어내지 않았다.

12 / BUSINESS APPLICATIONS

반복되는 지식 업무에서
작은 적용 단위를 찾는다.

아래는 강연을 바탕으로 한 작성자 제안 · 회사의 확정 계획이 아님

업무 적용 후보와 시작 조건
후보 업무필요한 입력기대하는 결과사람이 맡을 판단
주간 임원 브리핑회의 기록, 사업 지표, 전주 보고서변화·쟁점·결정 필요 사항을 근거와 함께 정리중요도와 최종 메시지 선정
제안서·교육 자료기존 제안서, 사례, 청중 정보관련 사례 재사용과 초안 제작고객 적합성, 핵심 논지, 공개 범위
프로젝트 인수인계결정 기록, 진행 문서, 결과물왜 그렇게 결정했는지와 남은 일을 설명현재 상태와 책임자의 확인
리서치 요약선별 기사·논문·시장 자료주제별 정리와 기존 판단과의 차이 파악출처 신뢰성과 해석의 타당성

우선순위는 ‘반복성 × 자료 준비도’로 정한다

자료가 이미 있고 결과물의 형식이 반복되는 업무가 첫 적용에 적합하다는 판단이다. 목적이 불분명하거나 원본이 흩어져 최신 상태를 알기 어려운 업무는 AI 기능보다 자료 정리를 먼저 해야 한다. 처음부터 모든 메신저·이메일·화면 기록을 연결할 필요는 없다.

첫 적용 후보

‘주간 임원 브리핑 초안’을 권장한다. 기존 보고서와 비교할 수 있고, 같은 업무를 반복하며 개선점을 확인하기 쉽다. 실제 회사 자료의 유무와 담당자의 사용 의향에 따라 확정한다.

13 / FOUR-WEEK PILOT

4주 동안 한 업무를 반복하며
실제 효용을 확인한다.

실행 일정 제안 · 승인 전 · 도입이나 자동화 실행을 완료한 것이 아님

WEEK 01 · 범위 설정

목적과 비교 기준을 정한다

업무 책임자와 함께 한 가지 결과물, 사용할 자료, 사람이 확인할 항목을 결정한다. 기존 방식의 작성 시간과 수정 시간을 기록한다.

완료 조건: 업무 범위 1장, 원본 목록, 비교할 기존 결과물 확보.

WEEK 02 · 지식 정리

필요한 자료만 위키로 만든다

원문·AI 정리본·사람의 판단을 구분하고 주제별 목차를 만든다. 출처와 날짜를 남기고 담당자가 대표 질문으로 자료를 찾아본다.

완료 조건: 대표 업무 질문의 근거를 원문까지 찾아갈 수 있음.

WEEK 03 · 초안 활용

실제 보고 업무에 사용한다

담당자와 단일 AI부터 시작해 자료 탐색과 초안 작성에 활용한다. 수정 사항, 재사용한 자료, 작성 시간을 기록한다. 필요가 드러날 때만 역할을 나눈다.

완료 조건: 실제 결과물과 수정 내역, 총 소요 시간 확보.

WEEK 04 · 확대 판단

시간과 품질을 함께 비교한다

자료 갱신과 운영 부담까지 포함해 기존 방식과 비교한다. 효과가 있는 범위는 유지하고 불필요한 수집이나 복잡한 운영은 줄인다.

완료 조건: 유지·보완·중단 중 하나를 책임자가 결정.

필요 역할은 세 가지다

업무 책임자는 목적과 최종 사용 여부를 결정한다. 지식 담당자는 원본·목차·갱신을 관리한다. 실무 사용자는 결과물을 만들고 수정 이력을 남긴다. 소규모에서는 한 사람이 여러 역할을 맡아도 된다. 시작부터 별도 전담 조직을 만들자는 제안은 아니다.

14 / COST & VALUE

초안 생성 시간보다
전체 업무 시간이 줄었는지 본다.

발표자는 데이터가 늘수록 관리 비용이 생기고, 모델·추론 수준과 지식 구조를 조정할 필요가 있다고 설명했다. 구체적인 구독료, 호출량, 회사 적용 비용은 제공되지 않았으므로 이 보고서는 금액이나 수익률을 추정하지 않는다.

총 운영 부담모델·도구 비용 + 자료 정리·갱신 시간
+ 결과 수정 시간 + 시스템 유지 시간
시범 운영에서 기록할 지표 · 작성자 제안
지표기록 방법판단하는 이유
전체 소요 시간탐색·작성·수정·갱신에 쓴 시간을 모두 기록생성은 빨라도 수정 부담이 늘면 이득이 줄어듦
근거 확인 가능성주요 주장 중 원문을 찾아 확인할 수 있는 항목 기록그럴듯한 초안과 업무에 쓸 수 있는 보고서를 구분
주요 수정 건수사실 오류·빠진 내용·논지 변경을 구분시간 절감과 결과 품질을 함께 확인
지식 재사용다음 결과물에 활용한 기존 자료를 기록한 번의 요약을 넘어 축적의 효과가 있는지 확인
사용 비용실제 청구·사용 기록과 담당자 투입 시간 집계효과에 비해 운영 부담이 과하지 않은지 확인

확대 기준의 구체적인 수치는 기존 업무의 수준을 측정한 뒤 정한다. 강연에서 언급된 개인 자동화율을 그대로 목표로 쓰거나 문서 수를 성과 지표로 삼는 것은 피한다.

주요 질의응답 정리

Obsidian을 반드시 사용해야 하나?

강연에서는 필수가 아니라고 설명했다. Markdown 중심의 편의 기능 때문에 사용하는 도구이며 다른 앱도 언급했다. 핵심은 특정 앱이 아니라 지식 구조와 활용 방식이다. [55:50–57:02]

여러 사람이 함께 쓰려면 어떻게 하나?

소규모 동기화, 위키를 관리하는 에이전트의 공유, 규모가 커질 경우 별도 데이터 관리 체계와 기존 사내 시스템의 연계가 언급됐다. 이는 확장 방향에 대한 의견이며 구체적인 전사 구축 설계는 제시되지 않았다. [105:33]

자료가 많아지면 느려지거나 찾지 못하나?

발표자는 자료가 많아질수록 무거워질 수 있고 주제별 분리가 필요하다고 말했다. 후반부에는 자료 양과 재사용 단위에 따라 2단계부터 최대 4단계의 목차 구조를 사용한다는 사례가 등장한다. 이는 개인 구성 사례다. [39:17, 57:52, 112:02 이후]

AI의 틀린 답변은 어떻게 받아들여야 하나?

발표자의 모델 평가와 환각 감소 체감은 개인 의견이다. 같은 질의응답에서 사람이 검색 결과 일부를 확인하고 중요한 발표물은 직접 확인한다는 취지도 언급됐다. 따라서 사람이 책임지는 확인 과정이 사라졌다고 해석할 수 없다. [109:45–112:02 이후]

메신저 연결에서 무엇이 중요한가?

누가 메시지를 볼지, 태그가 있어야 응답할지, 어느 채널로 답할지를 규칙으로 정하는 내용이 나왔다. 플랫폼별 봇 대화 제약에 대한 일부 발언은 발표자도 확인이 필요하다고 했으므로 이 보고서에서는 확정 사실로 채택하지 않았다. [112:02 이후]

모델과 추론 수준은 어떻게 골랐나?

글쓰기 취향, 오래 작업하는 성향, 역할별 요구, 사용 가능한 비용에 따라 조정한다는 개인 운영 사례였다. 특정 모델이 모든 업무에 최선이라는 비교 결과나 공통 구매 기준은 제시되지 않았다. [104:43–105:33 이후]
