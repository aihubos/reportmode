01

판단의 배경

메신저, 코드 저장소, 자동화, AI 에이전트의 경계를 하나의 서명 기록으로 합치려 합니다. 쉽게 비유하면 , Slack의 채널, GitHub의 코드 변경, 자동화 도구의 실행 기록, AI 에이전트의 작업을 한 건물 안으로 모으려는 프로젝트입니다. 사람과 에이전트는 모두 각자의 암호키로 행동에 서명하고, 메시지·승인·코드 이벤트가 같은 감사 기록에 남습니다. 채널·스레드·DM, 캔버스, 미디어, 검색, 감사로그, 데스크톱 앱, CLI, YAML 워크플로, Git 이벤트·호스팅. 모바일 앱, 워크플로 승인 게이트의 완전한 연결, 허들 수명주기 일부. 푸시 알림 등은 계획 단계입니다.

03

선택 기준과 판단

가장 익숙한 제품이 아니라 완료하려는 일로 고릅니다. 회사 업무·문서·회의·관리자 정책이 중심 이면 → Slack 게임·친구·팬 커뮤니티와 음성 대화가 중심 이면 → Discord 빠른 개인 메시지·대규모 그룹·방송 채널이 중심 이면 → Telegram AI 에이전트가 코드·워크플로·채널을 사람처럼 다루고, 서버와 감사 기록도 직접 통제 해야 하면 → Buzz 시험판 권고: Buzz를 기존 메신저의 즉시 교체재로 보지 말고, 비민감한 작은 개발 프로젝트에서 2~5명과 에이전트 1개로 시험하는 것이 맞습니다. 메시지 전달, 권한, 백업, 모바일 공백을 검증한 뒤 확대하세요.

04

주의점과 다음 행동

전문용어를 일상적인 비유로 바꾸면 구조가 보입니다. 하나의 URL이 하나의 작업공간 경계입니다. 채널·멤버·DM·검색·저장 데이터가 그 안에 묶입니다. 모든 앱과 에이전트가 릴레이에 연결됩니다. 릴레이는 서명을 확인하고 이벤트를 저장·검색·전달합니다. 메시지, 반응, 승인, Git 상태가 같은 모양의 서명된 기록입니다. 누가 무엇을 했는지 추적하기 쉽습니다. Nostr는 공개키 기반의 서명 이벤트 형식입니다. Buzz는 이를 회사용 작업공간처럼 확장합니다.

결론부터: Buzz는 “AI가 들어간 Slack”보다 더 큰 실험입니다

메신저, 코드 저장소, 자동화, AI 에이전트의 경계를 하나의 서명 기록으로 합치려 합니다.

한 문장 판단: Buzz는 메신저에 AI 챗봇을 붙인 제품이 아니라, 사람·AI 에이전트·코드·자동화를 하나의 기록 안에서 움직이게 하려는 개발자 중심 작업공간입니다.

쉽게 비유하면, Slack의 채널, GitHub의 코드 변경, 자동화 도구의 실행 기록, AI 에이전트의 작업을 한 건물 안으로 모으려는 프로젝트입니다. 사람과 에이전트는 모두 각자의 암호키로 행동에 서명하고, 메시지·승인·코드 이벤트가 같은 감사 기록에 남습니다.

어떤 서비스를 선택해야 하나

가장 익숙한 제품이 아니라 완료하려는 일로 고릅니다.

선택은 이렇게 하시면 됩니다

  • 회사 업무·문서·회의·관리자 정책이 중심이면 → Slack
  • 게임·친구·팬 커뮤니티와 음성 대화가 중심이면 → Discord
  • 빠른 개인 메시지·대규모 그룹·방송 채널이 중심이면 → Telegram
  • AI 에이전트가 코드·워크플로·채널을 사람처럼 다루고, 서버와 감사 기록도 직접 통제해야 하면 → Buzz 시험판

권고: Buzz를 기존 메신저의 즉시 교체재로 보지 말고, 비민감한 작은 개발 프로젝트에서 2~5명과 에이전트 1개로 시험하는 것이 맞습니다. 메시지 전달, 권한, 백업, 모바일 공백을 검증한 뒤 확대하세요.

Buzz는 내부에서 어떻게 움직이나

전문용어를 일상적인 비유로 바꾸면 구조가 보입니다.

1. 커뮤니티 = 한 회사 건물

하나의 URL이 하나의 작업공간 경계입니다. 채널·멤버·DM·검색·저장 데이터가 그 안에 묶입니다.

2. 릴레이 = 우체국+기록보관소

모든 앱과 에이전트가 릴레이에 연결됩니다. 릴레이는 서명을 확인하고 이벤트를 저장·검색·전달합니다.

3. 이벤트 = 서명된 업무 영수증

메시지, 반응, 승인, Git 상태가 같은 모양의 서명된 기록입니다. 누가 무엇을 했는지 추적하기 쉽습니다.

Nostr를 쓴다는 뜻

Nostr는 공개키 기반의 서명 이벤트 형식입니다. Buzz는 이를 회사용 작업공간처럼 확장합니다. 다만 Buzz의 기본 구조는 여러 릴레이가 자유롭게 복제하는 소셜 네트워크라기보다, 한 릴레이를 단일 진실 공급원으로 쓰는 팀 시스템입니다. “탈중앙화”라는 말만 보고 자동으로 완전한 익명성·E2EE·무중단 분산 시스템을 기대하면 안 됩니다.

장점과 단점

Buzz의 강점은 동시에 운영 부담이 될 수 있습니다.

✅ 에이전트가 손님이 아니다

각 에이전트가 자기 키·멤버십·감사 기록을 가지므로, 누가 어떤 행동을 했는지 사람과 같은 구조로 추적할 수 있습니다.

✅ 대화와 코드 기록을 붙인다

채널의 결정, 패치, CI, 리뷰, 승인 기록이 분리된 도구 사이에서 유실되는 문제를 줄이려는 설계입니다.

✅ 서버와 데이터 경계를 선택한다

직접 릴레이를 운영하면 메시지·미디어·멤버십을 선택한 하드웨어에 둘 수 있습니다.

⚠️ 셀프호스트는 버튼 하나가 아니다

Rust 릴레이 외에 Postgres, Redis, S3 호환 저장소, TLS, DNS, 키·비밀값·백업이 필요합니다.

⚠️ 초기 버그가 핵심 흐름에 있다

공개 이슈에는 에이전트 응답 손실, 권한 설정 불일치, 외부 에이전트 실시간 연결, 온보딩 혼란이 보고돼 있습니다.

⚠️ 모바일·알림·다국어가 약하다

모바일은 개발 중이며 푸시 알림은 계획 단계입니다. 현 UI는 영어 중심이고 한국어 현지화 요구도 공개 이슈에 있습니다.

소유권, 암호화, 운영 책임을 나눠 봐야 합니다.
