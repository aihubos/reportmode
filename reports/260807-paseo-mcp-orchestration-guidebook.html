EXECUTIVE SUMMARY

MCP는 리모컨이고,
오케스트레이션은 업무 지휘 방식입니다

PASEO MCP는 에이전트가 PASEO 데몬에 “다른 에이전트를 만들고, 작업공간을 정하고, 상태를 확인하고, 반복 실행을 등록하라”고 요청할 수 있게 하는 도구 모음입니다. 오케스트레이션은 그 도구를 이용해 역할과 순서를 설계하는 운영 방식입니다.78

한 문장 결론

PASEO를 잘 쓰는 핵심은 AI를 많이 띄우는 것이 아니라, “누가 계획하고·어디서 수정하고·누가 검증하며·언제 멈출지”를 먼저 정하는 것입니다. 일반 사용자는 MCP 도구명을 외우기보다 원하는 결과와 안전 조건을 자연어로 지시하면 됩니다.

01

MCP

PASEO 내부 자원인 Agent, Workspace, Terminal, Schedule을 AI가 조작하는 관리 도구층입니다.

02

Workspace

어디서 일할지를 정합니다. 독립 편집은 Worktree, 읽기 전용 병렬 조사는 같은 Workspace가 효율적입니다.

03

Parentage

누가 누구의 작업을 소유하는지 정합니다. 다른 Workspace에 보내도 부모·자식 관계는 유지됩니다.

04

Stop Rule

반복 작업에는 최대 횟수·시간·수용 기준·승인 지점을 반드시 넣어야 합니다.

설정 UI 대신 JSON으로 켜는 방법

daemon.mcp.enabled는 MCP 서버 자체를, injectIntoAgents는 새 Agent에 PASEO 도구를 주입하는 설정입니다.67

~/.paseo/config.json
{
  "$schema": "https://paseo.sh/schemas/paseo.config.v1.json",
  "version": 1,
  "daemon": {
    "listen": "127.0.0.1:6767",
    "hostnames": ["localhost", ".localhost"],
    "mcp": {
      "enabled": true,
      "injectIntoAgents": true
    }
  }
}

paseo.json으로 자동 준비

Worktree 생성 후 의존성을 설치하고, test·web service를 Agent와 MCP가 일관되게 실행하도록 등록할 수 있습니다.12

repo-root/paseo.json
{
  "worktree": {
    "setup": "npm ci"
  },
  "scripts": {
    "test": { "command": "npm test" },
    "lint": { "command": "npm run lint" },
    "web": {
      "type": "service",
      "command": "npm run dev -- --port $PASEO_PORT",
      "port": 3000
    }
  }
}

운영 시 기억할 점

1
paseo.json은 선택한 base branch의 committed 버전을 읽습니다.
2
Setup은 새 Worktree에 없는 dependency·설정 준비에 사용합니다.
3
Service는 $PASEO_PORT를 사용하면 여러 Worktree가 동시에 실행될 수 있습니다.
4
Windows에서도 재현되도록 POSIX 전용 cp/rm 대신 cross-platform npm script를 권장합니다.
보고서 판단: Worktree는 코드 충돌을 줄이는 격리이지, Agent의 파일·자격증명 접근을 막는 보안 Sandbox는 아닙니다. Provider 권한과 Mount·환경변수 범위를 별도로 통제해야 합니다.

COPYABLE RECIPES

실무에서는 아래 다섯 가지 패턴부터
복사해 시작하면 됩니다

모델 이름을 고정하기보다 “먼저 Provider·Model을 조회하라”고 지시하면 버전 변화에 강합니다. 모든 프롬프트에는 파일 범위·수용 기준·중지 조건·승인 지점을 넣었습니다.

01
Planner → Codex 구현 → 다른 Provider 독립 리뷰가장 표준적인 Cross-provider 개발 흐름
⌄
자연어 오케스트레이션 프롬프트
너는 Main Orchestrator로 남아 있어.

1. 사용 가능한 Provider와 Model을 먼저 조회해.
2. main을 기준으로 feature/parser-hardening 브랜치의
   Worktree-isolated Workspace를 만들어.
3. 가장 적합한 Codex Provider/Model을 Worker로 실행해.

Worker 업무:
- parser의 malformed input 처리 수정
- 관련 Test 추가
- focused Test와 Lint 실행
- 변경 파일과 Test 결과를 요약

수용 기준:
- 기존 Test와 새 Test 모두 통과
- 불필요한 API 변경 없음
- 변경 범위는 parser와 관련 Test로 제한

Worker가 완료되면 같은 Workspace에 다른 Provider의 Reviewer를 새로 만들어.
Reviewer는 대화 맥락을 공유받지 말고 현재 Diff와 Test 결과만 보고
정확성, 누락된 Test, 불필요한 복잡성을 독립 검토해.

Commit, PR 생성, Merge, 배포는 내 승인 전 금지해.
마지막에는 Worker 결과와 Reviewer 의견의 일치·불일치를 표로 보고해.

예상 도구 흐름

list_providers → list_models → create_workspace → create_agent → get_agent_status → 같은 Workspace에 Reviewer create_agent

CLI로 직접 실행할 때

paseo run --new-workspace worktree --worktree-mode branch-off --new-branch feature/parser-hardening --base main --provider codex "..."

이후 paseo workspace ls로 ID를 확인하고 paseo run --workspace <id> --provider claude "review current diff..."

안전장치: 구현과 리뷰를 같은 Worktree에 배치하되, Reviewer는 별도 Agent Session으로 만들어 대화의 자기합리화를 줄입니다.
02
세 Agent 병렬 조사 · 파일 수정 금지동일 Workspace에서 빠르게 이해 범위를 넓히는 패턴
⌄
Read-only Fan-out 프롬프트
현재 Workspace에 PASEO Subagent 3명을 만들어줘.
모두 파일을 수정하지 않는 읽기 전용 조사로 제한해.

A: 요청이 API에서 DB까지 흐르는 경로 추적
B: 관련 Test와 누락된 Edge case 조사
C: 최근 변경과 유사 회귀 사례 조사

각 Agent는 근거 파일 경로와 핵심 줄을 남기고,
서로의 결과를 보지 않은 상태로 독립 조사해.
세 명이 모두 완료되면 Main Agent가 공통점, 충돌, 추가 확인 항목을 종합해.
명령 실행은 읽기·Test 조회 범위로 제한하고 파일 변경은 금지해.

왜 같은 Workspace인가

읽기 전용이므로 파일 충돌이 없고, 세 Agent가 같은 코드 상태를 즉시 볼 수 있습니다.

예상 도구 흐름

create_agent × 3 → get_agent_activity → Main Agent 종합

03
CI를 끝까지 지켜보는 Heartbeat현재 대화를 유지하면서 주기적으로 재평가
⌄
Heartbeat 프롬프트
PASEO Heartbeat를 10분 간격으로 만들어줘.

현재 PR의 CI를 다시 확인하고,
새 실패가 생기면 로그를 분석해 원인을 수정한 뒤 focused check를 실행해.
의미 있는 변화가 있을 때만 이 대화에 보고해.

종료 조건:
- 모든 Check가 통과하면 Heartbeat 삭제
- 2시간이 지나면 중지하고 현재 상태와 차단 요인 보고
- 동일 실패가 3회 반복되면 자동 수정 중지 후 사람의 판단 요청
- Merge와 배포는 금지

Heartbeat가 맞는 이유

같은 Agent와 대화 맥락을 유지하면서 외부 상태 변화에 맞춰 다시 깨어납니다.

Skill 대안

/paseo-loop babysit PR 123 until checks are green, check every 10m, max-time 2h

04
매일 아침 새 Agent로 GitHub Triage같은 대화가 필요 없는 독립 반복 업무
⌄
Schedule 자연어 프롬프트
평일 오전 9시(Asia/Seoul)에 새 Agent를 시작하는 Schedule을 만들어줘.

업무:
- 새 Issue와 PR 확인
- 실패한 Check와 Review 대기 항목 확인
- 긴급도, 담당 필요 여부, 오늘 의사결정 항목을 표로 요약
- 파일 수정, PR Merge, Issue Close는 하지 않음

Schedule 이름은 morning-triage로 하고,
처음 생성한 뒤 1회 즉시 실행해 결과 형식을 확인시켜줘.
CLI 예시 · Asia/Seoul
paseo schedule create \
  --cron "0 9 * * 1-5" \
  --timezone Asia/Seoul \
  --run-now \
  --name morning-triage \
  --provider codex \
  --cwd ~/dev/my-app \
  "Review new issues, PRs, and failed checks. Summarize only; do not edit or merge."
Schedule은 실행마다 새 Agent를 만듭니다. 매일 깨끗한 맥락으로 같은 업무를 수행해야 할 때 Heartbeat보다 적합합니다.1314

네 곳부터 확인합니다

대부분의 초기 문제는 PASEO가 Provider 실행 파일을 찾지 못하거나, 기존 Agent가 새 MCP Tool을 받지 못한 경우입니다. 병렬 편집 문제는 Workspace 설계에서 발생합니다.17

1PASEO 도구가 보이지 않음

Enable Paseo tools를 켰지만 Agent가 도구를 못 찾는 경우입니다.

해결: daemon.mcp.enabled와 injectIntoAgents 확인 → 데몬 재시작 → 기존 대화 Reload 또는 새 Agent 생성.

2Provider가 Not installed

터미널에서는 되지만 PASEO의 PATH에는 실행 파일이 없는 경우가 많습니다.

해결: Diagnostic의 Resolved path·Daemon PATH 확인 → which -a 또는 where.exe 비교 → 새 로그인 셸에서 보이도록 수정 후 재시작.

3Reviewer가 변경 파일을 못 봄

Worker와 Reviewer를 서로 다른 Workspace에 둔 경우입니다.

해결: 구현 후 Reviewer는 Worker와 같은 Workspace·Worktree에 만들고 대화 Session만 분리합니다.

4두 Worker가 같은 파일을 덮어씀

독립 편집 과제를 같은 Workspace에서 병렬 실행한 경우입니다.

해결: 과제별 Worktree Workspace를 생성하고, 완료 후 Diff 단위로 비교·Merge합니다.

5Browser Tool 호출 오류

MCP Tool은 켰지만 Browser Tools가 꺼져 있거나 Desktop Browser Host가 연결되지 않은 경우입니다.

해결: Host → Agents에서 Browser tools도 켜고 Desktop을 연결. 로그인된 세션에 접근하므로 신뢰 Agent만 허용.

6Loop가 끝나지 않음

수용 기준이 모호하거나 최대 시간·반복 횟수가 없는 경우입니다.

해결: Pass/Fail Check, max-iterations, max-time, 동일 실패 N회 시 사람 호출 조건을 함께 지정.

Provider 경로를 직접 고정하는 예시

PASEO가 PATH를 계속 찾지 못하면 agents.providers.<id>.command에 실행 파일 절대 경로를 지정할 수 있습니다.

config.json · macOS 예시
{
  "agents": {
    "providers": {
      "codex": {
        "command": ["/opt/homebrew/bin/codex"]
      }
    }
  }
}

Windows 절대 경로 예시

JSON에서는 역슬래시를 두 번 써야 합니다. 실제 경로는 where.exe codex 결과를 사용합니다.

config.json · Windows 예시
{
  "agents": {
    "providers": {
      "codex": {
        "command": [
          "C:\\Users\\me\\AppData\\Local\\bin\\codex.exe"
        ]
      }
    }
  }
}
보안 원칙: PASEO는 Provider의 기존 인증을 사용하며, Relay 연결은 종단간 암호화를 제공합니다. 다만 Pairing QR·링크는 신뢰의 기준이므로 비밀번호처럼 취급하고, Browser Tools는 로그인 세션까지 다룰 수 있으므로 필요한 Host와 Agent에만 켭니다.16
