DON’T FREEZE

한 번의 실패를 최종 한계로 보지 않는다

모델이 약했을 수도 있지만, 목표·input·원자료·도구 경로가 잘못됐을 가능성도 먼저 본다.

SEPARATE

사실, 회사 주장, 내 관찰, 전망을 나눈다

확인된 것과 기대하는 것을 같은 문장에 섞지 않으면 과장도 줄고 수정도 쉬워진다.

KEEP CONTROL

실행과 외부 발신은 사람이 끝낸다

초안은 AI가 빨리 만들 수 있다. 결제·삭제·발송·공개·의사결정은 승인 단계를 남긴다.

ONE-MINUTE BRIEF

낙관과 검증은 반대말이 아니었다

AI의 미래를 크게 보는 사람일수록 오늘의 출력물을 더 냉정하게 봐야 한다. 지금의 오류를 숨기면 발전을 이용할 수 없고, 지금의 오류만 보고 포기하면 다음 기회를 놓친다.

한 문장 결론

AI의 미래를 믿는 태도와 오늘의 출력물을 의심하는 습관은 모순이 아니라 같은 운영 원칙이다.

나는 AI에게 먼저 묻는다. 하지만 결론과 책임까지 넘기지는 않는다. 검수는 꼭 사용자가 한다.

CAPABILITY+30%p

Stanford AI Index 2026은 frontier model의 Humanity’s Last Exam 점수가 1년 새 30%p 올랐다고 정리했다. [출처 1]

LONG TASKS196.5일

METR TH1.1의 장기 추세 fit은 P50 time horizon 배증을 약 196.5일로 추정한다. 특정 task suite 기반 지표다. [출처 3]

ERROR RANGE22~94%

AI Index가 소개한 한 accuracy benchmark에서 26개 상위 모델의 환각률 범위다. 모든 업무의 일반 오류율은 아니다. [출처 2]

FINAL OWNER1명

외부 공개·발송·삭제·결제 전에 최종 책임자를 명시한다. 내 원칙은 단순하다. 사용자가 끝낸다.

THE DISAPPOINTING MOMENT

“AI티가 많이 나네”라는 말을 들었을 때

회사에서 글로벌 스마트폰 동향 초안을 AI로 만들었던 적이 있다. 내 나름대로는 빠르게 만들었다고 생각했는데, 돌아온 말은 짧았다.

처음에는 솔직히 실망했다

문장은 맞는 것 같았지만 회사 형식에 맞지 않았다. 비즈니스 문구도 아니었고, 핵심 숫자와 영향이 없는 빈껍데기 문장이 섞여 있었다.

그 순간 “아직 AI는 이 정도인가”라고 생각할 수도 있었다. 충분히 그렇게 느낄 수 있다. 나도 결과를 보고 답답했으니까.

하지만 나는 다르게 보기로 했다. AI가 못한 것인지, 내가 일을 제대로 정의하지 못한 것인지부터 나눠봤다.

REAL SCENE · 작성자 경험
“아직은 AI티가 많이 나네.”

이 말은 AI가 영원히 못한다는 판정이 아니었다. 회사 양식, Raw Data, 핵심 질문, Reference를 내가 충분히 주지 않았다는 신호에 가까웠다.

↻

현재의 실패는 데이터다

현재 내가 사용하는 AI는 앞으로 사용할 AI 중 가장 부족한 AI 중 하나다. 그렇다고 오늘의 오류를 무시하자는 뜻은 아니다. 실패 원인을 기록해 다음 input과 workflow를 바꾸자는 뜻이다.

ROOT-CAUSE CHECK

AI가 틀렸을 때, 모델 탓은 마지막에 한다

생성형 AI는 불확실할 때 그럴듯하게 추측할 수 있다. OpenAI 연구는 평가 구조가 “모르겠다”보다 추측을 보상하는 문제가 환각을 지속시키는 한 원인이라고 설명한다. 그래서 결과만 다시 뽑기보다 실패 지점을 분리해야 한다. [출처 5]

01

Goal

증상
내용은 많지만 “그래서 무엇을 결정해야 하는지”가 없다.
확인
독자, 결정, 마감, 출력 형식을 한 문장으로 말할 수 있는가.
다음
“누가 무엇을 판단할 문서인지”부터 다시 쓴다.
02

Input

증상
장점만 늘어놓거나 일반론을 반복한다.
확인
원하는 관점, 금지할 표현, 비교 기준을 줬는가.
다음
좋은 답 예시와 나쁜 답 예시를 함께 넣는다.
03

Raw Data

증상
숫자가 없거나 출처 없는 숫자가 생긴다.
확인
공식 원문, PDF, 표, 확인일을 제공했는가.
다음
모르는 숫자는 비워두고 “확인 필요”로 표시하게 한다.
04

Reference

증상
회사 문체와 디자인에서 벗어난다.
확인
기존 보고서, 템플릿, 금지어, 길이를 보여줬는가.
다음
내용을 복사하지 말고 구조와 기준을 따라가게 한다.
05

Tool / Path

증상
PDF 표를 못 읽거나 파일은 만들었다는데 열리지 않는다.
확인
텍스트 모델 하나로 모든 단계를 처리하려 했는가.
다음
웹·PDF·코드·파일·스크린샷 도구로 경로를 바꾼다.
06

Model

증상
모든 조건을 줘도 반복적으로 같은 한계가 난다.
확인
다른 모델, 더 작은 단계, 다른 언어로 교차 시험했는가.
다음
모델을 바꾸거나, 사람이 맡을 단계로 명확히 남긴다.
FAIL → FIX → USE

실패를 수정으로 바꾸는 4단계

성공은 AI가 한 번에 완벽한 답을 낸 순간이 아니었다. 어디가 비었는지 확인하고 다시 검수 가능한 형태로 만든 순간에 가까웠다.

01

거친 초안

“글로벌 스마트폰 동향 정리해줘”처럼 범위가 넓고 판단 기준이 없는 요청.

02

재료 고정

공식 원문, 기간, 비교 기준, 회사 용어, 표 구조를 먼저 붙인다.

03

불확실성 표시

사실·회사 주장·추정·내 관찰을 라벨로 나누고 빈칸은 남긴다.

04

사람이 끝내기

숫자·원문·문장·파일을 열어보고 결론과 발신 여부를 최종 결정한다.

CHANGE THE PATH

한 도구가 막히면, 답을 재생성하기보다 구현 경로를 바꾼다

같은 채팅창에서 열 번 다시 묻는 것보다 원문을 열고, 코드를 실행하고, 파일을 실제로 확인하는 편이 빠를 때가 많다.

작업막히는 방식바꿀 경로완료 증거
최신 사실 조사모델 기억만으로 답을 확정공식 페이지 → 원문 PDF → 신뢰도 높은 보도 순서로 확인URL, 게시일, 확인일, 해당 문장
PDF·표·차트검색 요약만 읽고 숫자를 사용원문 페이지를 직접 열고 표·그림 페이지를 확인페이지 번호, 표 제목, 단위
코드·자동화코드 블록이 그럴듯하면 완료로 간주테스트 환경에서 실행하고 실패 로그를 읽음exit code, 테스트 결과, 생성 파일
파일 생성“완료했습니다”라는 문장만 믿음파일 존재·크기·형식·열림 여부를 검사실제 경로, hash, 미리보기
외부 발신초안과 실행을 한 단계로 묶음Draft → 사람 승인 → Send로 분리승인자, 시각, 발신 기록
FACT VS FORECAST

예측과 확인된 사실을 같은 문장에 넣지 않는다

AI 성능이 빠르게 좋아지는 것은 확인할 수 있다. 하지만 그 추세가 언제, 어떤 업무에서, 어느 수준까지 이어질지는 전망이다. METR도 time horizon을 특정 task suite와 50% 성공 확률로 측정하며, 실제 자율 실행 시간과 같은 뜻이 아니라고 설명한다. [출처 3]

CONFIRMED

확인된 사실

공식 문서·논문·원문에서 직접 확인했고 기준일을 붙인 내용. 문장 끝에 출처를 둔다.

COMPANY CLAIM

회사 주장

기업이 발표한 benchmark·로드맵·효과. 사실처럼 쓰지 않고 “회사 측 결과”라고 표시한다.

OBSERVATION

내 관찰

내 workflow에서 반복해 본 경험. 유용하지만 모든 사람에게 그대로 일반화하지 않는다.

FORECAST

전망

×세 모델이 같은 답을 냈으니 사실이다

SIX OPERATING PRINCIPLES

낙관과 검증을 함께 유지하는 6가지 원칙

“AI는 미래다”라는 확신을 실행으로 바꾸려면 믿음보다 workflow가 필요하다.

01

실패를 판정이 아니라 기록으로 본다

안 된 이유와 재현 조건을 남긴다. 다음 모델과 다음 workflow의 input이 된다.

02

원인을 분리한다

Goal, input, Raw Data, Reference, Tool, Model을 한꺼번에 탓하지 않는다.

03

모른다고 말하게 한다

확신도, 빈칸, 추가 확인 항목을 출력 형식에 포함한다.

04

경로를 바꾼다

웹, PDF, 코드, 파일, 다른 모델을 사용해 답이 아니라 증거를 만든다.

05

검수 가능한 산출물로 끝낸다

링크, 표, 로그, 파일, diff처럼 사람이 확인할 수 있는 흔적을 남긴다.

06

최종 권한은 사용자에게 둔다

삭제·결제·발송·공개·중요 결정은 사람 승인 없이는 실행하지 않는다.

30 / 60 / 90 DAYS

검수를 습관에서 시스템으로 바꾸는 방법

처음부터 거대한 AI 거버넌스를 만들 필요는 없다. 작은 체크리스트에서 시작해 실제 실패 데이터로 키우면 된다.

30 DAYS

5개 체크리스트 고정

자주 쓰는 보고서·블로그·코드 workflow에 원문, 숫자, 라벨, 실행, 승인 5개 항목을 붙인다.

  • 초안과 외부 실행 분리
  • 출처 확인일 기록
  • 실패 로그 한 줄
60 DAYS

내 업무 평가 세트 만들기

실제 자주 하는 20~50개 과제를 모아 모델과 프롬프트를 같은 조건에서 비교한다.

  • 정확도보다 완료 기준
  • 사람 수정 시간 측정

FAQ

자주 생기는 질문

AI가 자꾸 틀리면 그냥 쓰지 않는 게 낫지 않나요?
그렇게 생각할 수도 있다. 다만 초안, 분류, 구조화, 검색 시작점처럼 오류를 빨리 발견할 수 있는 업무에서는 여전히 큰 가치가 있다. 중요한 건 사용 여부를 한 번에 결정하는 것이 아니라, AI가 맡을 단계와 사람이 맡을 단계를 나누는 것이다.
여러 모델이 같은 답을 내면 검증된 것 아닌가요?
아니다. 모델들이 같은 웹 문서, 학습 데이터, 잘못된 전제를 공유할 수 있다. 모델 간 합의는 보조 신호일 뿐이고, 최종 근거는 독립된 원문·실행 결과·관측 데이터여야 한다.
모든 AI 출력에 원문 검수가 필요한가요?
개인 아이디어 메모와 대외 공개 문서는 검수 강도가 달라야 한다. 영향이 작고 쉽게 되돌릴 수 있으면 빠른 확인으로 충분할 수 있다. 숫자, 법률, 의료, 재무, 계약, 외부 발신, 삭제·결제는 강화 검수를 권한다.
AI 에이전트가 더 똑똑해지면 사람 검수는 사라질까요?
검수의 형태는 바뀔 수 있다. 모든 문장을 사람이 읽기보다 평가 세트, monitor, 권한, 승인, 예외 처리로 이동할 가능성이 크다. 하지만 책임과 목표를 정하는 역할까지 자동으로 사라진다고 단정하기는 어렵다.
검수 때문에 오히려 일이 느려지지 않나요?
처음에는 그렇다. 그래서 자주 틀리는 항목만 체크리스트로 만들고, 낮은 위험 업무는 표본 검사를 쓰는 편이 좋다. 반복될수록 검수도 자동화할 수 있지만, 외부 실행 승인만큼은 분리해두는 것이 안전하다.
