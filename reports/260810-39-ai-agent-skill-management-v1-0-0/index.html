PROBLEM

세션이 바뀌면 교정도 사라졌다

한 번 잘한 경험이 다음 실행의 절차로 고정되지 않으면, 같은 설명과 같은 수정이 다시 필요했습니다.

TURNING POINT

사실은 메모리, 방법은 스킬

취향과 배경은 기억에, 명령·단계·실패 조건·검증은 별도의 실행 문서에 나눠 남겼습니다.

VERDICT

실패한 순간이 업데이트 타이밍

좋은 스킬은 완성본이 아니라, 실제 사용 중 틀린 단계를 바로 고치는 살아 있는 매뉴얼입니다.

ONE-MINUTE BRIEF

에이전트의 경험은 대화에 남기면 추억이고, 스킬에 남기면 다음 실행이 됩니다

안녕하세요, 비서조련사 제레미입니다. AI도 어제 배운 걸 오늘 또 까먹습니다. 사람 같아서 반갑지는 않았습니다 ㅎㅎ

JEREMY'S VERDICT

메모리를 더 많이 넣는다고 반복 실수가 자동으로 줄어들지는 않았습니다. 실행 순서와 검증 기준이 적힌 스킬이 있어야 어제의 시행착오가 오늘의 능력이 됩니다.

Hermes 공식 가이드도 메모리를 ‘무엇을 아는가’, 스킬을 ‘어떻게 하는가’에 가까운 절차 지식으로 구분합니다. [출처 2]

SKILL절차·검증

단계, 명령, 실패 모드, 완료 조건을 필요할 때만 불러옵니다. [출처 2]

UPDATE실패 직후

같은 수정을 두 번 설명하기 전에, 틀린 단계와 검증 규칙부터 패치합니다.

THE REPEATED MISTAKE

한 세션 안에서는 잘했는데, 새 대화가 열리면 다시 처음이었습니다

처음에는 제가 설명을 덜 했다고 생각했습니다. 그래서 메모리를 더 넣고, 긴 프롬프트도 붙였습니다. 그런데 문제는 정보량이 아니라 실행 순서가 고정되지 않은 데 있었습니다.

제가 반복해서 겪은 흐름

어제는 잘 끝냈습니다. 중간에 오류가 났지만 원인을 찾았고, 마지막에는 결과도 검수했습니다.

SESSION A오류 발견 → 원인 수정 → 결과 확인
SESSION B같은 작업 요청 → 같은 단계 누락 → 같은 오류
MY RESPONSE“어제 이거 고쳤잖아”를 다시 설명
REAL PROBLEM고친 내용이 다음 실행의 규칙으로 남지 않음
대화가 길어졌다고 경험이 쌓인 것은 아니었습니다. 다음 세션이 읽고 따라 할 수 있는 형태로 남아야 비로소 재사용됩니다.

그래서 잘된 답변을 저장하는 대신, 잘되기까지의 순서와 실패 조건을 스킬로 바꾸기 시작했습니다.

MEMORY VS SKILL

메모리는 “제레미가 무엇을 좋아하는지”, 스킬은 “이 일을 어떻게 끝내는지”를 남깁니다

둘 중 하나가 더 좋은 것이 아닙니다. 서로 다른 것을 저장해야 에이전트가 덜 헷갈립니다.

MEMORY · WHAT

짧게 항상 알아야 할 것

사용자 정보, 선호, 고정된 배경처럼 매 세션에 도움이 되는 사실입니다.

1“제레미는 짧은 호흡의 글을 선호한다”
2“Report Hub는 Toss Blue를 사용한다”
3“외부 게시 전에는 사용자 승인이 필요하다”
SKILL · HOW

필요할 때 불러오는 실행 매뉴얼

어떤 상황에서, 어떤 도구로, 어떤 순서와 기준으로 일을 끝낼지 적습니다.

1입력과 선행 조건을 먼저 확인
2명령과 단계, 예외 처리 순서를 실행
3완료 조건을 검증하고 실패하면 중단
구분남기는 것적합한 예주의할 점
메모리사실·취향·짧은 맥락사용자 선호, 기본 저장 위치, 팀 용어긴 절차를 넣으면 매 세션의 문맥을 계속 차지함
프롬프트이번 요청의 목표오늘 한 번만 필요한 수정·질문다음 세션에 자동 재사용되지 않음
도구하나의 원자적 행동파일 읽기, 검색, 명령 실행어떤 순서로 조합할지는 별도 지침이 필요
스킬반복 가능한 절차 지식보고서 패키징, 배포 전 QA, PR 리뷰낡으면 잘못된 방법을 빠르게 반복하는 부채가 됨
승인형 워크플로확정된 실행 경로와 권한 경계외부 발신, 결제, 삭제, 프로덕션 변경스킬만 믿지 말고 guardrail·사람 승인·로그를 함께 둠 [출처 8]
ANATOMY OF A GOOD SKILL

좋은 스킬에는 멋진 설명보다 단계·명령·실패 조건·검증이 있습니다

Hermes 공식 예시는 When to Use, Procedure, Pitfalls, Verification을 기본 뼈대로 제시합니다. 저는 여기에 입력 조건과 중단 기준, 업데이트 규칙을 더합니다. [출처 2]

01

Trigger

언제 사용하고 언제 사용하지 않을지 적습니다. 설명이 너무 넓으면 엉뚱한 작업에 불립니다.

02

Inputs

필요한 파일, 권한, 경로, 설정, 원자료를 먼저 확인합니다. 준비가 없으면 실행하지 않습니다.

03

Procedure

순서와 명령을 그대로 재현할 수 있게 씁니다. 판단이 필요한 지점은 기준까지 남깁니다.

04

Failure

자주 틀리는 부분, 재시도 조건, 즉시 멈춰야 할 위험 신호를 적습니다.

05

Verification

파일 존재, 테스트 통과, 수치 일치처럼 “끝났다”를 증명하는 확인 절차를 둡니다.

BEFORE / AFTER

스킬 전후의 차이는 답변 품질보다 재설명과 재검수의 양에서 먼저 보였습니다

아래는 특정 벤치마크가 아니라 제가 운영할 때 확인하는 비교 기준입니다. 스킬이 있다고 모델이 무조건 더 똑똑해지는 것은 아닙니다. 대신 실수의 종류와 수정 위치가 눈에 보이기 시작합니다.

작업 지점스킬 전스킬 후남는 자산
새 세션 시작작업 목적과 순서를 다시 설명설명과 작업이 맞으면 스킬을 먼저 불러옴재사용 가능한 trigger
명령 실행에이전트가 매번 새 계획을 추론검증된 명령·순서에서 시작하고 상황에 맞게 조정실행 runbook
오류 발생대화 안에서 원인을 찾고 세션 종료 후 사라짐pitfall과 stop condition에 실패 원인을 추가다음 실행의 예방 규칙
완료 판단그럴듯한 답변을 완료로 착각할 수 있음파일·테스트·수치·링크를 별도 검증acceptance criteria
운영 개선“다음에는 잘해줘”로 끝남틀린 문장만 patch하고 새 세션에서 재시험버전형 절차 지식
WHEN A SKILL GOES STALE

낡은 스킬은 실수를 줄이는 도구가 아니라 실수를 자동화하는 도구가 됩니다

Hermes 문서도 실제 사용 중 문제가 드러나면 스킬을 업데이트하라고 권합니다. 유지되지 않는 스킬은 부채가 될 수 있습니다. [출처 2]

01

같은 수동 수정이 두 번 나왔다

사람이 같은 부분을 다시 고쳤다면, 대화가 아니라 스킬의 해당 단계가 틀린 것입니다.

02

명령 옵션이나 출력 형식이 바뀌었다

도구가 업데이트됐는데 예전 flag와 경로를 쓰면, 정확하게 오래된 방법을 반복합니다.

03

엉뚱한 요청에 스킬이 실행된다

`description`이 너무 넓거나 모호한 신호입니다. 스킬은 이름과 설명을 먼저 보고 활성화됩니다. [출처 4]

04

검증은 통과했는데 결과가 틀렸다

검증 명령이 너무 약하거나 성공 조건이 실제 목적과 맞지 않은 경우입니다.

05

한 스킬이 너무 많은 일을 한다

수정 하나가 다른 작업까지 흔듭니다. 한 문장으로 책임을 설명하기 어렵다면 분리할 시점입니다.

06

누가 언제 고쳤는지 알 수 없다

버전, 변경 이유, 마지막 검증일이 없으면 잘못된 수정도 경험처럼 굳어질 수 있습니다.

⚠
민감한 스킬은 자동 수정까지 맡기지 않습니다. Hermes는 에이전트가 스킬을 생성·수정·삭제할 수 있고, `skills.write_approval`로 모든 변경을 사람 승인 대기 상태로 둘 수 있습니다. 운영·보안·외부 발신 스킬에는 승인 게이트를 켜는 편이 안전합니다. [출처 3]

# Report Hub Publish

## When to Use
- A topic must become a standalone HTML report and upload ZIP.
- Existing report data, sources, or metadata must be updated safely.

## Do Not Use
- The user only wants a short text answer.
- The source material is missing and the core claim cannot be verified.

## Inputs
- Topic, publish date, daily sequence, repository, template
- Source URLs or files
- Required output structure and approval boundary

## Procedure
1. Read the project instructions, voice profile, template, and prior version.
2. Verify current names, dates, prices, licenses, and source status.
3. Draft the article in the requested voice; label assumptions and unverified claims.
4. Generate `index.html`, `thumbnail.png`, `thumbnail.svg`, metadata, and source ledger.
5. Build the ZIP without overwriting archive or sitemap files that were not read.
6. Run QA and fix failures before presenting the files.

## Commands / Tools
- Use the official source first; use trusted reporting only to fill gaps.
- Run HTML, JSON schema, image-size, link-security, and ZIP-manifest checks.
- Use targeted patches for small changes; do not rewrite an unrelated section.

## Failure / Stop Conditions
- Stop if a key number has no source or two authoritative sources conflict.
- Stop before GitHub push, external publishing, payment, deletion, or message sending unless the user explicitly approves it.
- Do not mark the task complete while required files or checks are missing.

## Verification
- The HTML title, H1, OG title, canonical, version, and metadata agree.
- Thumbnail is exactly 1200×630 and the `<img>` alt text is meaningful.
- Mobile width has no page-level horizontal overflow.
- ZIP paths, file hashes, and upload manifest agree.
- Every external link has `target="_blank" rel="noopener noreferrer"`.

## Update Rule
When a failure is corrected, patch the exact step, pitfall, or verification rule in this skill. Record what changed and re-run the smallest test that proves the correction.

FAQ

처음 스킬을 만들 때 가장 많이 생기는 질문

메모리와 스킬의 가장 큰 차이는 무엇인가요?
메모리는 사용자 사실과 취향처럼 “무엇을 아는지”에 가깝고, 스킬은 특정 일을 “어떤 순서와 기준으로 수행할지”에 관한 절차 지식입니다. Hermes 공식 가이드도 이 구분을 그대로 설명합니다. [출처 2]
반복 프롬프트는 모두 스킬로 만들어야 하나요?
아닙니다. 반복 가능성, 단계 수, 실패 비용, 검증 필요성이 충분할 때만 스킬로 만드는 편이 좋습니다. 단순 선호는 메모리, 일회성 요청은 프롬프트, 위험한 외부 실행은 승인형 워크플로로 분리합니다.
SKILL.md는 얼마나 길어야 하나요?
공개 Agent Skills 문서는 메인 파일을 500줄 이하로 유지하고, 긴 자료는 `references/`, 실행 코드는 `scripts/`, 템플릿은 `assets/`로 분리하도록 권장합니다. 중요한 것은 길이보다 trigger와 핵심 절차가 한눈에 보이는지입니다. [출처 4]
Hermes가 스킬을 자동으로 만들거나 수정할 수 있나요?
가능합니다. Hermes는 복잡한 작업 성공, 오류 우회, 사용자 교정, 비정형 workflow 발견 후 스킬을 만들거나 수정할 수 있습니다. 민감한 환경에서는 `skills.write_approval`을 켜서 모든 변경을 승인 대기 상태로 둘 수 있습니다. [출처 3]
스킬이 제대로 작동하는지는 어떻게 확인하나요?
작성한 세션이 아니라 새 세션에서 같은 입력으로 시험합니다. 정상 입력뿐 아니라 파일 누락, 잘못된 경로, 권한 부족 같은 실패 입력도 넣고, 검증 명령이 실제 오류를 잡는지 확인합니다.
처음 만들기 좋은 스킬은 무엇인가요?
최근 한 달 안에 두 번 이상 반복했고, 매번 3단계 이상 진행하며, 마지막에 사람이 결과를 확인했던 작업이 좋습니다. 보고서 패키징, 배포 전 QA, 정기 데이터 정리처럼 성공 기준이 명확한 일이 시작하기 쉽습니다.
