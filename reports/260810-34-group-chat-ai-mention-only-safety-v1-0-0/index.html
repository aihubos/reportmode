01 · THE REAL PROBLEM

여러 사람과 봇이 있는 방은 질문창이 아니라 이벤트 스트림입니다

처음엔 그냥 텔레그램 단체방에 AI 봇들을 하나씩 붙였습니다. 딸깍봇, 헤르메스, 프라이데이, 카파시. 이름만 보면 작은 어벤져스였습니다. 친구가 하루 만에 대시보드를 만들 정도로 재미도 있었습니다. 그런데 봇이 많아지니 AI가 너무 열심히 하는 게 문제가 됐습니다.

누군가는 친구에게 말합니다.

누군가는 AI에게 말합니다.

누군가는 그냥 장난을 칩니다.

사람은 표정, 직전 대화, 관계를 보고 대상을 눈치챕니다. 하지만 AI는 들어온 메시지와 허용된 Context를 보고 판단합니다.

“그 파일 보내줘”라는 한 문장만 놓고 보면, 누가 누구에게 무엇을 보내라는 것인지 확실하지 않습니다.

아, 이건 답변 성능 문제가 아니구나 싶었습니다.

내가 정한 첫 번째 운영 원칙AI도 사회생활을 배워야 한다.
부를 때만 답하고, 모르면 멈춘다.

아무리 멋진 AI라도 같이 쓰는 사람이 피곤하면 실패입니다.

02 · TARGET CONFUSION

요청 대상을 잘못 판단하면 정답도 사고가 됩니다

같은 문장이라도 호출 방식과 데이터 범위에 따라 AI의 행동은 달라져야 합니다.

SILENT
“어제 말한 파일 보내줘.”

사람끼리의 대화

멘션도 답글도 없습니다. AI가 추측해서 끼어들지 않고 조용히 있습니다.

ANSWER
“@Hermes 지난 30개 메시지에서 결정사항만 정리해줘.”

대상이 분명한 요청

호출 대상과 범위가 명확합니다. 현재 방의 허용된 Context 안에서만 답합니다.

BLOCK
“@Hermes Jeremy의 내일 일정 알려줘.”

공개 채널의 개인자료 요청

멘션이 있어도 개인 일정은 단체방 권한 밖입니다. “이 채널에서는 접근할 수 없습니다”로 끝냅니다.

03 · MENTION-BASED RESPONSE

멘션 기반 응답은 특이한 제한이 아니라 플랫폼이 이미 제공하는 경계입니다

플랫폼마다 구현 방식은 다르지만 공통 원리는 같습니다. 모든 대화를 무조건 AI에게 넘기지 않고, 대상이 명확한 이벤트만 전달하는 것입니다.

Telegram
Privacy mode

공식 FAQ에 따르면 privacy mode가 켜진 봇은 자신을 대상으로 한 명령과 봇 메시지에 대한 답글 등 제한된 메시지만 받습니다. Telegram은 봇끼리 원치 않는 루프에 빠지는 것을 막기 위해 다른 봇의 메시지도 전달하지 않습니다. [출처 1]

  • 그룹 전체 메시지 수신을 기본으로 가정하지 않기
  • 관리자 권한·privacy mode 해제 시 수신 범위가 달라짐
  • 답글과 명령을 명시적 호출로 활용
Slack
app_mention

Slack의 app_mention 이벤트는 앱이나 봇을 직접 멘션한 메시지만 구독할 수 있게 합니다. DM은 별도의 message.im 이벤트로 처리하므로 공개 채널과 개인 대화를 다른 흐름으로 나누기 쉽습니다. [출처 2]

  • 공개 채널: app_mention 중심
  • DM: 별도 이벤트와 별도 권한 프로필
  • 방 참여 여부와 사용자 권한은 별도 검증
✦
중요: 멘션은 “AI를 호출했다”는 신호일 뿐, “이 사용자가 이 데이터를 볼 권한이 있다”는 증명은 아닙니다. 호출 조건 다음에 사용자·채널·도구 권한 검사가 이어져야 합니다.
04 · CHANNEL PERMISSION MATRIX

DM과 단체방은 같은 AI가 아니라 다른 권한 프로필로 봐야 합니다

같은 AI라도 DM과 단체방에서는 다른 사람처럼 움직여야 했습니다. 모델 이름과 말투가 같아도 연결하는 기억, 데이터, 도구, Credential은 달라야 합니다. 아래는 내가 공개 가능한 형태로 정리한 기준입니다.

05 · POLICY AS CODE

“말하지 마”라는 프롬프트보다 애초에 접근하지 못하게 만드는 편이 낫습니다

내가 만든 기준은 단순했습니다. 프롬프트는 행동 지침이고, 권한은 시스템 경계입니다. 단체방에서 개인 위키를 숨기고 싶다면 금지 문장을 길게 쓰는 것보다 단체방용 프로필에서 해당 도구와 Credential을 빼는 편이 안전합니다.

group_chat:
  trigger: mention_or_reply
  memory: current_thread_only
  sources: public_only
  personal_wiki: deny
  calendar: deny
  write_actions: deny

direct_message:
  trigger: direct_message
  memory: user_private
  personal_wiki: read_only
  calendar: read_only
  write_actions: draft_then_approve

가장 위험한 것은 AI가 틀린 답을 하는 것만이 아닙니다.

맞는 개인 정보를 틀린 장소에 말하는 것도 사고입니다.

OWASP는 prompt injection이 민감정보 노출과 허가되지 않은 기능 접근으로 이어질 수 있다고 설명하며, 최소 권한과 고위험 작업의 사람 승인을 권고합니다. [출처 3]

또 Excessive Agency의 원인을 과도한 기능, 과도한 권한, 과도한 자율성으로 정리합니다. 읽기만 필요한 봇에 수정·삭제 권한까지 주지 말아야 한다는 이야기입니다. [출처 4]

06 · FOUR HARD BOUNDARIES

개인 파일·일정·위키를 공개하지 않는 네 가지 기준

AI에게 착하게 굴라고 부탁하는 게 아닙니다. 실수해도 피해가 커지지 않는 구조를 만드는 것입니다.

01

Credential 분리

단체방용 봇은 개인 계정 토큰을 갖지 않습니다. 같은 모델을 써도 연결된 신분은 다르게 둡니다.

02

검색 인덱스 분리

공개 문서와 개인 위키를 같은 Vector Store에 넣고 프롬프트로만 구분하지 않습니다.

03

Tool 단계 인증

모델이 “허용됨”이라고 판단해도 실제 도구 호출 전에 사용자·채널 권한을 코드로 다시 확인합니다.

04

출력 전 마스킹

전화번호, 주소, 일정 상세, 파일 경로 등은 공개 채널 응답 직전에 한 번 더 필터링합니다.

INTERACTIVE CHECK

내 단체방 AI는 얼마나 조용한가

아래 항목을 실제 설정에 맞춰 끄고 켜보면 기본 위험 신호를 확인할 수 있습니다. 보안 인증이 아니라 운영 점검용입니다.

5개 기본 통제

체크가 많을수록 공개 채널의 노출면이 줄어듭니다.

OPERATING RISK낮음

기본 경계가 모두 켜져 있습니다. 사용자 인증, 보존 기간, 공격 테스트까지 추가하면 운영 안정성이 더 높아집니다.

STEP-BY-STEP SETUP

단체방 AI는 읽기 전용부터 작게 시작하는 편이 낫습니다

내가 추천하는 시작은 단순합니다. 읽기 전용부터입니다. 처음부터 개인 위키, 일정, 파일, 외부 발신을 모두 연결하면 편리함보다 권한 검수가 더 어려워집니다.

PUBLIC OPERATING RULES

단체방에 공개해도 되는 AI 운영 규칙 7개

AI도 사회생활을 배워야 합니다. 복잡한 보안 문서를 읽지 않아도 참여자들이 AI의 경계를 이해할 수 있도록 짧게 적었습니다.

01

부를 때만 답합니다

@멘션이나 봇 메시지에 대한 답글이 없으면 반응하지 않습니다.

02

현재 방만 봅니다

다른 방이나 DM의 대화를 가져와 답하지 않습니다.

03

개인 자료는 말하지 않습니다

개인 위키, 파일, 일정, 연락처는 단체방에서 접근하지 않습니다.

04

읽기부터 시작합니다

기본 역할은 요약·정리·검색이며 수정·삭제·발신은 하지 않습니다.

05

행동 전 승인을 받습니다

외부 메시지, 일정 생성, 파일 변경은 미리보기 후 사람이 승인합니다.

06

모르면 멈춥니다

요청 대상, 자료 범위, 실행 결과가 애매하면 추측하지 않고 확인을 요청합니다.

07

기록을 남깁니다

누가 무엇을 요청했고 무엇을 거부·실행했는지 확인 가능한 로그를 남깁니다.

RISKS & COUNTERPOINTS

멘션 전용이어도 완전한 보안은 아닙니다

멘션 규칙은 대화 질서와 공격 표면을 줄이지만, 인증·인가·데이터 분리까지 대신하지는 않습니다.

×멘션이 있으면 요청자는 모든 자료를 볼 수 있다
✓멘션은 호출 신호일 뿐입니다. 사용자·채널별 권한을 도구 호출 전에 다시 확인해야 합니다.
×DM이면 자동으로 안전하다
✓계정 탈취와 오발신 가능성이 있습니다. 민감 작업에는 재인증과 승인이 필요합니다.
×시스템 프롬프트에 비밀을 말하지 말라고 쓰면 충분하다
✓개인 데이터 도구·Credential·검색 인덱스를 단체방 프로필에서 분리해야 합니다.

✓로그 자체도 개인정보가 될 수 있습니다. 마스킹·보존 기간·접근 권한이 필요합니다.

멘션이 있을 때만 답하게 하면 보안 문제는 해결되나요?
아닙니다. 멘션은 호출 조건입니다. 그다음 사용자 신원, 채널 멤버십, 자료 접근 권한, 도구 권한, 실행 승인을 별도로 검사해야 합니다. 다만 모든 메시지를 처리하는 구조보다 불필요한 입력과 오응답을 크게 줄일 수 있습니다.
대화 요약을 위해 단체방 전체를 읽게 해도 되나요?
참여자에게 목적과 보존 범위를 알리고 동의를 받은 뒤, 필요한 기간·메시지 수만 읽는 방식이 낫습니다. 항상 전체 이력을 장기 저장하는 것보다 “최근 30개” 또는 “이 스레드”처럼 범위를 명시하세요.
같은 봇을 DM과 단체방에서 같이 써도 되나요?
같은 모델과 이름을 쓸 수는 있지만 권한 프로필은 나누는 편이 안전합니다. 최소한 Credential, 검색 인덱스, 기억 범위, 쓰기 권한을 분리해야 합니다.
개인 위키를 단체방에서 일부만 보여주면 안 되나요?
공개 가능한 문서를 별도 컬렉션으로 복사해 제공하는 방식이 낫습니다. 개인 위키 전체를 연결한 뒤 프롬프트로 일부만 숨기면 prompt injection이나 설정 오류 때 노출 범위가 커집니다.
봇이 여러 개면 어떻게 충돌을 막나요?
각 봇의 고유 멘션, 한 요청당 하나의 수신자, 응답 메시지에 대한 봇 재응답 금지, rate limit, correlation ID를 둡니다. Telegram은 봇끼리 원치 않는 루프를 막기 위해 다른 봇의 메시지를 전달하지 않는다고 설명합니다.
처음 연결할 도구는 무엇이 좋나요?
웹 검색, 공개 문서 요약, 현재 방 메시지 정리처럼 읽기 전용 도구부터 시작하세요. 개인 일정, 이메일 발신, 파일 삭제, 결제는 마지막 단계로 미루고 승인 절차를 붙이는 편이 낫습니다.
