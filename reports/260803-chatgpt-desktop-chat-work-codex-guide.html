01

판단의 배경

비전공자에게 가장 중요한 기준은 “얼마나 기술적인가”가 아니라 “답변이 필요한가, 실제 결과물이 필요한가, 구현 과정까지 통제해야 하는가”입니다. 비전공자가 Codex를 쓰는 이유는 코드를 배우기 위해서만이 아닙니다. 폴더 안의 여러 파일을 읽고, 실제 파일을 만들거나 바꾸고, 명령을 실행해 결과를 확인하며, 변경 내역을 검수 가능한 형태로 남겨야 할 때 가치가 생깁니다. 다만 보고서·발표자료·스프레드시트처럼 일상 업무 결과물이 목적이라면 ChatGPT Work가 더 쉬운 기본값입니다. 설명, 아이디어, 짧은 초안, 비교와 조언. 결과는 주로 대화 안에 있습니다.

02

핵심 비교와 근거

공식 문서는 Work와 Codex의 핵심 능력이 겹친다고 설명합니다. 차이는 주로 시작 위치, 보이는 기술 정보, 결과를 제시하는 방식입니다. 파일과 도구를 직접 다루는 기술 작업대 “이 자료로 8장 발표자료를 만들어 주세요.” “이 폴더에서 웹페이지를 만들고 실제로 열어 검증해 주세요.” 문서·발표·스프레드시트·PDF·분석·반복 업데이트 코드·사이트·스크립트·파일 변경·테스트·변경 내역 완성 결과 중심, Git·셸 세부는 숨기는 편 diff·리뷰·명령·구현 세부를 볼 수 있음 파일 시스템·자동화·웹 제작처럼 구현 통제가 필요할 때 단순 질문에 시간·크레딧을 더 쓸 수 있음 기술 정보가 과하고 잘못된 파일 변경 위험이 커짐 업로드를 반복…

03

선택 기준과 판단

가장 작은 유용한 모드부터 시작하고, 필요할 때만 더 강한 실행 권한으로 올라갑니다. 지금 필요한 것이 답변인가? → Chat 검토해서 바로 쓸 문서·표·발표·분석인가? → Work 폴더·파일·코드·명령을 실제로 바꾸고, 어떻게 바뀌었는지 자세히 보고 싶은가? → Codex 개인적인 권고: 비전공자는 Work를 기본 작업실로 두고, “실제 폴더에서 구현·자동화·검증”이 필요한 순간에 Codex로 넘어가는 방식이 가장 쉽습니다. Codex를 선택해도 최종 검수 책임은 사용자에게 남습니다.

04

주의점과 다음 행동

기능 수가 아니라 완료 조건으로 판단해야 합니다. 예를 들어 “홈페이지 만들어 줘”라는 답변을 받는 데서 끝나지 않고, 실제 폴더에 HTML·CSS·이미지를 만들고 브라우저에서 열어 확인할 수 있습니다. 파일명 정리, 형식 변환, CSV 정제처럼 규칙이 있는 일을 스크립트나 작업 흐름으로 만들어 다시 쓸 수 있습니다. 어떤 파일을 만들고 무엇을 고쳤는지 기술 세부와 변경 보기를 통해 확인할 수 있습니다. 공식 문서도 Work가 비코딩 일상 업무를 위해 설계된 경험이라고 설명합니다. 기술 세부가 필요 없다면 Codex는 과할 수 있습니다.

결론부터: 세 모드는 경쟁자가 아니라 작업의 깊이가 다릅니다

비전공자에게 가장 중요한 기준은 “얼마나 기술적인가”가 아니라 “답변이 필요한가, 실제 결과물이 필요한가, 구현 과정까지 통제해야 하는가”입니다.

한 문장 판단: 답이 필요하면 Chat, 완성된 업무 결과물이 필요하면 Work, 파일·코드의 구현 과정까지 보고 통제하려면 Codex가 맞습니다.

비전공자가 Codex를 쓰는 이유는 코드를 배우기 위해서만이 아닙니다. 폴더 안의 여러 파일을 읽고, 실제 파일을 만들거나 바꾸고, 명령을 실행해 결과를 확인하며, 변경 내역을 검수 가능한 형태로 남겨야 할 때 가치가 생깁니다. 다만 보고서·발표자료·스프레드시트처럼 일상 업무 결과물이 목적이라면 ChatGPT Work가 더 쉬운 기본값입니다.

Codex를 써야 하는 이유와 쓰지 않아도 되는 이유

기능 수가 아니라 완료 조건으로 판단해야 합니다.

✅ 이유 1 · 말이 아니라 파일이 남는다

예를 들어 “홈페이지 만들어 줘”라는 답변을 받는 데서 끝나지 않고, 실제 폴더에 HTML·CSS·이미지를 만들고 브라우저에서 열어 확인할 수 있습니다.

✅ 이유 2 · 반복 작업을 절차로 바꾼다

파일명 정리, 형식 변환, CSV 정제처럼 규칙이 있는 일을 스크립트나 작업 흐름으로 만들어 다시 쓸 수 있습니다.

✅ 이유 3 · 변경 내역이 보인다

어떤 파일을 만들고 무엇을 고쳤는지 기술 세부와 변경 보기를 통해 확인할 수 있습니다.

⚠️ 이유 1 · 일상 문서에는 Work가 더 쉽다

공식 문서도 Work가 비코딩 일상 업무를 위해 설계된 경험이라고 설명합니다. 기술 세부가 필요 없다면 Codex는 과할 수 있습니다.

⚠️ 이유 2 · 실제 변경은 실제 위험을 만든다

잘못된 폴더, 덮어쓰기, 명령 실행, 외부 전송은 대화 오류보다 영향이 큽니다. 처음에는 Ask for approval을 유지해야 합니다.

⚠️ 이유 3 · 더 긴 작업은 더 많은 사용량을 쓸 수 있다

Work와 Codex는 가격·크레딧·사용 한도를 공유합니다. 복합 작업은 결과 가치가 클 수 있지만 단순 질문보다 비용이 커질 수 있습니다.

비전공자용 15분 시작법

처음부터 전체 폴더를 맡기지 말고 최소 시험판으로 시작합니다.

  1. 앱 설치: 공식 다운로드에서 Windows 또는 macOS용 ChatGPT 데스크톱 앱을 설치합니다.
  2. 작은 시험 폴더: 원본의 복사본 5~10개만 새 폴더에 넣습니다.
  3. 모드 선택: 설명이면 Chat, 완성 문서면 Work, 실제 폴더 변경이면 Codex를 선택합니다.
  4. 권한: 처음에는 Ask for approval을 사용합니다. Full access로 시작하지 않습니다.
  5. 프롬프트: 목적·입력·금지사항·완료 조건·검증 방법을 씁니다.
  6. 미리보기 후 실행: 먼저 계획과 예상 변경 목록만 요청하고, 승인 뒤 복사본에 적용합니다.
  7. 검수: 생성 파일을 직접 열고 숫자·이름·날짜·누락·원본 보존을 확인합니다.

복사해서 쓰는 실제 활용 프롬프트 8개

아래 문구는 실제 실행 결과가 아니라 안전 경계와 검증 조건을 포함한 재사용용 템플릿입니다.

1. 폴더 정리 시험판 · 권장: Codex

결과: 정리 계획 CSV, 복사본 폴더, 검증 보고서

[목적] 이 폴더의 파일을 연도/월/종류 기준으로 정리할 시험판을 만드세요.
[입력] ./inbox-test 안의 파일만 사용하세요.
[안전 경계] 원본 파일은 이동·삭제·이름 변경하지 마세요. 외부 전송 금지. 먼저 proposed_moves.csv에 원본 경로, 제안 경로, 이유를 작성하고 멈추세요.
[실행] 제가 승인한 뒤 ./organized-preview에 복사본만 만드세요. 이름 충돌은 덮어쓰지 말고 -2, -3을 붙이세요.
[완료 조건] 원본 수와 복사본 수, 누락·중복·충돌 수가 포함된 verification.md를 만드세요.
[중단 조건] 날짜나 종류를 확신할 수 없는 파일은 unknown에 제안만 하고 임의 분류하지 마세요.

검수: 샘플 10개 경로, 원본 개수, 중복 해시를 직접 확인합니다.

2. 지저분한 CSV 정리 · 권장: Work 또는 Codex

결과: cleaned.csv와 data-quality.md

[목적] @sales-export.csv의 날짜·통화·중복·지역명을 정리한 새 CSV를 만드세요.
[원본 보존] 원본은 절대 수정하지 마세요.
[규칙] 날짜는 YYYY-MM-DD, 통화는 숫자 열로 통일하되 빈칸은 빈칸으로 유지하세요. source_row_id를 보존하세요. 요약 행은 데이터와 분리하세요.
[검증] 처리 전후 행 수, 제거한 중복 기준, 변환 실패 행, 열별 빈값 수를 data-quality.md에 기록하세요. 합계가 원본과 달라지면 원인을 설명하세요.
[완료 조건] cleaned.csv를 다시 읽어 열 수 있고 모든 행의 열 개수가 같아야 합니다.
[중단 조건] 중복 판정 키가 불명확하면 삭제하지 말고 질문하세요.

  • 제품과 문서는 빠르게 변합니다. 이 보고서는 2026.08.03 KST의 공식 문서 스냅샷입니다.
