EXECUTIVE SUMMARY

영상이 전달하는 결론은 “도구 교체”보다 “제작 방식의 전환”입니다

발표 내용을 먼저 정리하고, AI에게 디자인 기준과 대본을 구조화해 제공하면 장표 디자인과 애니메이션 작업을 크게 단축할 수 있다는 것이 영상의 핵심 주장입니다.

한 문장 결론

HTML 발표 자료의 강점은 예쁜 디자인 자체가 아니라, 화면 크기에 맞춰 비율을 유지하고, 발표자의 말 흐름에 따라 요소를 단계적으로 보여주며, 사용자의 마우스 행동에 반응하게 만들 수 있다는 점입니다.

01

AI에게 먼저 기준을 줍니다

폰트 · 컬러 · 비율 · 레퍼런스

“깔끔하게 만들어줘”보다 구체적인 디자인 규칙과 참고 이미지별 특징을 지정해야 결과의 일관성이 높아집니다.

02

본문 2장부터 완성합니다

작게 만들고 크게 확장

전체 슬라이드를 한 번에 생성하지 않고 핵심 본문 2장을 충분히 수정한 뒤, 그 스타일을 나머지 장표에 적용합니다.

03

대본이 애니메이션 설계도가 됩니다

엔터로 순차 등장

슬라이드별 대본을 제공하고 말의 순서에 맞춰 요소가 등장하도록 요청하면 발표 속도와 화면 전개를 맞출 수 있습니다.

WHY HTML

영상에서 강조한 HTML 발표 자료의 네 가지 장점

영상은 HTML을 PPT와 PDF의 장점을 일부 결합한 형태로 설명합니다. 특히 여러 화면에서 동일한 경험을 제공하고 동적 표현을 넣는 데 초점을 둡니다.

글꼴 일관성

다른 컴퓨터나 모바일에서도 지정한 디자인을 유지할 수 있어, PPT에서 자주 발생하는 글꼴 깨짐 문제를 줄일 수 있다고 설명합니다.

영상의 표현: “어떤 디바이스로 보든 지정한 폰트 그대로”

가벼운 공유

도형과 그래프를 코드로 표현하기 때문에 많은 시각 요소를 파일에 쌓는 PPT보다 가볍게 공유할 수 있다는 장점을 제시합니다.

핵심 의미: 파일 전달과 웹 배포가 쉬워짐

대본 기반 애니메이션

발표 대본의 흐름을 Claude에 제공하고, 엔터를 누를 때 다음 요소가 나타나도록 요청해 순차 전개를 빠르게 구현합니다.

발표 효과: 설명과 화면의 타이밍을 맞춤

상호작용

옵션에 마우스를 올리면 해당 카드만 강조하거나, 접힌 상세 정보가 펼쳐지는 등 PPT에서 구현하기 까다로운 반응을 만들 수 있습니다.

활용 예: 상품 소개서·옵션 비교·제안서
PPT VS HTML

HTML이 항상 더 좋은 것은 아닙니다

영상의 경험을 기준으로 보면, HTML은 동적 표현과 배포에 강하고 PPT는 마우스로 빠르게 세부 편집하는 데 유리합니다. 발표 목적에 따라 선택해야 합니다.

PPT가 편한 상황

마우스로 즉시 미세 조정해야 할 때

여백, 줄 간격, 요소 위치처럼 작은 디자인을 계속 바꾸는 과정에서는 직접 드래그하는 방식이 빠릅니다.

1
회의 직전 문구와 위치를 즉석에서 수정
2
팀원이 기존 PPT 편집 방식에 익숙함
3
복잡한 상호작용보다 정적인 전달이 중요
HTML이 빛나는 상황

여러 화면과 동적 전개가 중요할 때

비율을 유지한 반응형 화면, 단계적 애니메이션, 마우스 반응을 하나의 파일 또는 웹페이지로 제공할 수 있습니다.

✓
노트북·모바일·다양한 화면에서 공유
✓
대본 순서에 맞춘 단계별 등장
✓
옵션 비교·상품 소개처럼 사용자 반응이 필요
7-STEP WORKFLOW

영상의 제작법을 일곱 단계로 압축하면

결과물의 품질은 코드를 직접 잘 쓰는가보다, 내용을 구조화하고 AI에게 수정 기준을 얼마나 구체적으로 전달하는가에 좌우됩니다.

01

내용 정리

Notion 등에 슬라이드별 메시지와 데이터를 먼저 정리합니다.

02

디자인 기준

폰트, 컬러, 16:9 비율, 레퍼런스의 특징을 지정합니다.

03

본문 2장 제작

전체가 아닌 2·3번 슬라이드만 먼저 디자인합니다.

04

세부 검수

그래프 값, 핵심 문장, 여백, 줄 간격, 배치를 수정합니다.

05

전체 확장

확정한 2장을 디자인 기준으로 나머지 장표를 생성합니다.

06

대본 생성

완성된 장표와 원문을 바탕으로 슬라이드별 대본을 만듭니다.

07

모션·반응

엔터 순차 등장과 hover 확장 등 동적 요소를 추가합니다.

PROMPT PLAYBOOK

좋은 결과를 만드는 프롬프트는 “예쁘게”가 아니라 “검수 기준”을 말합니다

영상에서 반복해서 사용한 요청 방식을 하나의 재사용 가능한 프롬프트 구조로 정리했습니다. 아래 문구는 영상 내용을 요약·재구성한 예시입니다.

01 · SCOPE

전체보다 2장부터

“본문 2장만 먼저 디자인하고, 내가 승인한 뒤 나머지를 확장해줘.”

02 · SCALE

16:9 비율 유지

“화면 크기가 달라도 모든 요소가 같은 비율로 확대·축소되게 해줘.”

03 · VALIDATE

수치와 줄바꿈 검수

“그래프 길이를 실제 값과 맞추고, 한국어 단어가 중간에서 끊기지 않게 해줘.”

04 · REVEAL

대본 순서로 등장

“내가 엔터를 누를 때마다 다음 설명 요소가 나타나게 해줘.”

통합 요청 예시

첨부한 발표 내용으로 반응형 HTML 발표 자료를 만들어줘.

[디자인 기준]
- 화면 중앙의 16:9 슬라이드
- 화면 크기가 달라도 전체 비율을 유지해 확대·축소
- 배경색, 메인색, 보조색, 텍스트색을 일관되게 적용
- 레퍼런스별로 지정한 특징을 반영

[제작 순서]
1. 먼저 본문 2장만 디자인
2. 그래프 값과 막대 길이를 실제 수치에 맞춤
3. 핵심 메시지가 슬라이드 제목보다 더 잘 보이게 구성
4. 한국어 단어가 중간에서 끊기지 않게 처리
5. 승인된 2장의 스타일로 전체 슬라이드 확장

[발표 동작]
- 제공한 대본 순서에 맞춰 요소를 배치
- 엔터를 누를 때마다 다음 요소가 등장
- 옵션 카드에 마우스를 올리면 해당 카드의 상세 정보가 자연스럽게 펼쳐지게 구성
핵심은 한 번에 완성본을 요구하는 것이 아니라, 시안 → 검수 → 확장 → 모션의 순서로 AI 작업을 나누는 것입니다.
RISKS & CHECKS

AI가 빠르게 만들어도, 정확성과 디테일은 자동으로 보장되지 않습니다

영상 속 제작 과정에서도 첫 결과의 그래프 값, 배치, 여백, 문장 줄바꿈이 어색해 여러 차례 수정했습니다. “생성 속도”와 “완성도 검수”를 분리해야 합니다.

×처음부터 전체 슬라이드를 한 번에 완성하려고 함
✓핵심 본문 2장을 먼저 완성하고 디자인 언어를 고정한 뒤 확장
×그래프가 보기 좋으면 실제 값도 맞을 것이라고 가정
✓막대 길이, 수치, 증가 시점, 설명 순서를 원데이터와 대조
×“좀 더 예쁘게”처럼 모호한 수정 지시
✓여백, 정렬, 제목 비중, 아이콘 위치, 펼침 방향을 구체적으로 설명
×애니메이션을 많이 넣을수록 발표가 좋아진다고 판단
✓대본의 말 순서와 이해 흐름을 기준으로 필요한 요소만 단계적으로 등장
검수 원칙: 영상에서 제시한 장점은 발표자의 제작 사례를 바탕으로 한 설명입니다. 실제 업무 적용 시에는 사용 환경에서 글꼴, 링크, 애니메이션, 화면 비율, 오프라인 재생 여부를 직접 테스트해야 합니다.
WHEN TO USE

어떤 발표부터 HTML로 바꿔볼 것인가

모든 장표를 한꺼번에 전환하기보다, HTML의 장점이 분명한 발표 한 건을 골라 제작 시간과 전달 효과를 비교하는 방식이 현실적입니다.

PPT를 유지해도 좋은 경우

정적인 보고, 잦은 현장 수정, 공동 편집이 중심이라면 익숙한 PPT가 더 효율적일 수 있습니다.

1
텍스트와 수치를 마지막 순간까지 자주 바꾸는 보고
2
팀 전원이 드래그 방식의 공동 편집을 해야 하는 자료
3
애니메이션·상호작용보다 인쇄와 배포가 우선인 문서

HTML로 먼저 시험할 발표

화면 적응, 단계적 전개, 옵션 비교가 전달력에 직접 영향을 주는 발표가 적합합니다.

✓
상품 소개서 또는 서비스 옵션 비교
✓
교육·강의처럼 대본 순서와 화면 전개가 중요한 자료
✓
웹 링크로 공유하고 모바일에서도 보여줘야 하는 제안서
✓
마우스 hover로 세부 정보를 보여주고 싶은 데모
