WHAT I LEARNED

모델, KV 캐시, 브라우저, 코딩 도구, 운영체제가 같은 통합 메모리 풀을 함께 사용합니다.

MY RULE

로컬과 클라우드를 나눕니다

민감한 반복 작업은 로컬, 최고 품질과 최신 검증이 필요한 작업은 클라우드로 보냅니다.

ONE-MINUTE BRIEF

128GB는 속도를 사는 옵션이 아니라 가능한 실험의 범위를 사는 옵션이었습니다

내가 얻은 결론은 의외로 단순했습니다. 메모리 용량이 커지면 큰 모델을 올릴 수는 있습니다. 하지만 ‘올라간다’와 ‘매일 쓸 만하다’는 전혀 다른 이야기였습니다.

REPORT HUB VERDICT

CPU는 속도를 결정하지만, 메모리는 가능성을 결정합니다. 다만 128GB도 양자화·컨텍스트·동시 실행을 무시할 수 있는 무적키는 아닙니다.

큰 모델 하나를 겨우 올리는 것보다, 조금 작은 모델을 빠르게 반복하고 브라우저·위키·코딩 도구를 함께 쓰는 쪽이 실제 업무에서는 더 나을 때가 많았습니다. 그래서 모델 이름보다 ‘완료된 작업당 시간’을 봐야 합니다.

01

통합 메모리는 큰 작업대

CPU와 GPU가 같은 메모리를 직접 쓰기 때문에 대형 모델을 다루기 유리합니다. 하지만 운영체제와 앱도 같은 작업대를 씁니다. [출처 6]

02

컨텍스트도 메모리입니다

같은 모델이라도 컨텍스트를 늘리면 KV 캐시가 커집니다. 문서를 길게 넣거나 에이전트를 돌릴수록 여유분이 필요합니다. [출처 8]

03

큰 모델이 항상 정답은 아닙니다

답변 품질이 조금 좋아져도 첫 응답, 생성 속도, 발열, 동시 실행이 불편하면 실제 사용 빈도는 떨어집니다.

클라우드 AI는 편합니다. 하지만 내 파일, 개인 위키, 코드, 대화 기록을 계속 읽는 나만의 자비스를 만들려면 로컬에서 돌아가는 모델도 직접 운영해봐야 한다고 생각했습니다.

처음부터 목표는 벤치마크 1등이 아니었습니다.

인터넷이 없어도 돌아가고, 개인 자료를 외부로 보내지 않고, 내가 원하는 도구와 연결할 수 있는 AI.

그런 환경을 만들고 싶었습니다.

그래서 메모리는 최대한 크게 잡았습니다.

1컨텍스트를 늘리면 KV 캐시가 커짐

THE OPERATING REALITY

모델이 올라간다고 항상 실용적인 것은 아니었습니다

로컬 LLM은 ‘실행 성공’만 보면 판단을 틀리기 쉽습니다. 나는 같은 질문을 반복해서 아래 다섯 가지를 함께 봅니다.

LOAD시작 시간

모델 다운로드가 아니라 메모리에 올라가 사용할 수 있을 때까지.

TTFT첫 응답

질문을 보낸 뒤 첫 토큰이 화면에 나오는 시간.

DECODE생성 속도

초당 토큰뿐 아니라 긴 답을 끝까지 기다릴 수 있는지.

MEMORY여유분

브라우저와 코딩 도구를 같이 켰을 때 메모리 압력.

A

모델 크기

파라미터 수는 참고값입니다. Dense와 MoE는 구조가 다르고, MoE도 전체 weights는 메모리에 올라가야 하는 경우가 많습니다.

B

양자화

4-bit, 5-bit, 8-bit는 메모리와 속도, 품질의 균형이 다릅니다. ‘가장 큰 모델의 가장 낮은 비트’가 항상 최선은 아닙니다. [출처 7]

C

컨텍스트와 동시 실행

같은 모델도 긴 문서와 여러 세션을 붙이면 메모리 사용량이 달라집니다. KV 캐시 양자화도 별도 판단입니다. [출처 8] [출처 9]

MEMORY PLANNER

모델 이름보다 먼저 메모리 예산을 계산해봤습니다

아래 계산기는 계획용입니다. 실제 GGUF·MLX 파일 크기와 런타임 메모리는 모델 구조, 양자화 그룹, KV 캐시, 프레임워크 버전에 따라 달라집니다. 그래도 ‘들어가느냐’만 보는 것보다 훨씬 현실적인 출발점이 됩니다.

MoE는 active가 아니라 메모리에 올릴 전체 weights 기준으로 잡는 편이 안전합니다.

BUYING QUESTIONS

로컬 LLM 장비를 고를 때는 사양표보다 질문표가 먼저였습니다

무조건 128GB를 추천하는 글은 아닙니다. 내가 실제로 어떤 모델과 작업을 돌릴지에 따라 적정 메모리가 달라집니다.

01

정말 큰 모델이 필요한가?

7~14B급으로 충분한 분류·요약 작업인지, 30B·70B급 추론이 필요한지 먼저 나눕니다.

02

컨텍스트는 얼마나 필요한가?

짧은 채팅과 64K 이상 에이전트·코딩 작업은 같은 메모리 계획이 아닙니다.

03

무엇을 같이 켜둘 것인가?

브라우저, IDE, Docker, Obsidian, 벡터DB를 동시에 쓰면 모델 전용 여유가 줄어듭니다.

04

한 번에 몇 명이 쓸 것인가?

개인 1세션과 여러 에이전트·가족·팀 사용은 KV 캐시와 서버 구성이 달라집니다.

05

로컬이 필요한 이유가 분명한가?

개인정보, 오프라인, 반복 비용, 커스터마이징 중 무엇을 얻으려는지 적습니다.

06

관리할 마음이 있는가?

모델 다운로드, 런타임 업데이트, 라이선스, 장애 로그를 직접 다룰 시간이 필요합니다.

07

SSD 2TB는 충분한가?

여러 양자화와 모델 버전, 캐시, 데이터셋을 쌓으면 저장공간도 빠르게 줄어듭니다.

08

클라우드 비용과 비교했는가?

하드웨어 일시비용과 API 월비용, 전기·관리 시간을 같은 기간으로 비교합니다.

✓
구매 기준: 128GB는 ‘지금 꼭 필요한 모델’이 아니라 ‘앞으로 직접 실험하고 운영할 범위’에 돈을 쓰는 선택입니다. 로컬 LLM이 목적이 아니라면 과한 옵션일 수 있습니다.

  • 브라우저와 단일 런타임

  • 컨텍스트와 세션 제한
  • 메모리 압력 기록
  • 품질 대비 속도 비교
128GB

  • 그래도 full precision 대형 모델은 별도

FAQ

로컬 LLM용 MacBook을 고를 때 가장 많이 생기는 질문

128GB MacBook이면 70B 모델을 무조건 돌릴 수 있나요?
4-bit 70B 모델의 이론 가중치 값은 약 35GB입니다. 하지만 실제로는 양자화 메타데이터, 런타임 버퍼, KV 캐시, macOS와 다른 앱의 메모리가 추가됩니다. 대부분의 조합에서 충분한 후보가 될 수 있지만 ‘무조건’이라고 말할 수는 없습니다. 위 계산기와 실제 파일 크기로 확인해야 합니다.
통합 메모리 128GB는 전부 GPU 전용 VRAM인가요?
아닙니다. Apple silicon의 CPU와 GPU는 같은 메모리 풀에 직접 접근하고, 운영체제와 앱도 그 풀을 함께 사용합니다. 이것이 큰 모델을 올리기 쉬운 이유이면서 동시에 다른 앱과 메모리를 나눠 써야 하는 이유입니다. [출처 6]
RAM과 SSD 중 무엇을 먼저 올려야 하나요?
로컬 LLM에서 RAM은 실행할 모델과 컨텍스트의 상한을 크게 좌우하고, SSD는 모델 파일과 데이터 저장량을 좌우합니다. MacBook은 구매 후 메모리를 늘릴 수 없으므로 실행 범위가 중요하면 RAM을 먼저 봅니다. 다만 여러 모델과 양자화를 보관하면 2TB도 관리가 필요합니다.
4-bit 모델이 가장 합리적인가요?
많은 경우 좋은 출발점이지만 정답은 아닙니다. 5-bit나 8-bit가 품질 대비 속도에서 더 나을 수 있고, 작은 모델의 높은 정밀도가 큰 모델의 낮은 정밀도보다 유용할 때도 있습니다. 동일 과제로 비교하는 것이 가장 안전합니다.
컨텍스트를 크게 잡으면 왜 느려지나요?
프롬프트를 처리하는 prefill 시간이 늘고 KV 캐시 메모리도 증가할 수 있기 때문입니다. Ollama도 컨텍스트 길이를 늘리면 필요한 메모리가 증가한다고 안내합니다. [출처 8]
로컬 LLM이 클라우드 AI를 대체할까요?
개인 운영에서는 완전 대체보다 혼합이 현실적입니다. 민감 문서, 반복 작업, 오프라인은 로컬이 좋고, 최신 사실 조사, 고난도 추론, 외부 도구 연결, 최종 교차 검수는 클라우드가 더 나을 수 있습니다.
가장 먼저 기록할 성능 지표는 무엇인가요?
로드 시간, TTFT, prefill tokens/s, decode tokens/s, peak memory, 메모리 압력, 실제 과제 품질, 실패 유형입니다. 특히 모델 버전과 런타임 버전을 같이 남겨야 나중에 결과가 바뀐 이유를 찾을 수 있습니다.
