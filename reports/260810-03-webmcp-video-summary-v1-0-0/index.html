ONE-MINUTE SUMMARY

영상의 결론은 간단합니다. AI가 웹을 ‘보는’ 대신 ‘호출’하게 하자

사람을 위해 만든 버튼과 메뉴를 AI가 매번 해석하게 하는 대신, 웹사이트가 자신의 기능을 명시적인 도구로 공개하자는 것이 WebMCP의 핵심입니다. Chrome 공식 문서도 이를 에이전트의 클릭·입력 시뮬레이션보다 더 명확한 상호작용 방식으로 설명합니다. 출처 2

한 문장 결론

WebMCP는 웹사이트가 기능을 구조화된 도구로 공개해 AI가 화면을 추측하지 않고 호출하게 하는 제안이지만, 현재는 Chrome Origin Trial 단계이며 권한·프롬프트 인젝션·브라우저 종속 문제가 남아 있습니다.

영상의 큰 방향은 공식 문서와 일치합니다. 다만 ‘W3C 정식 표준’, ‘전체 인터넷의 60%가 AI’, ‘Gemini가 이미 일반 지원’으로 읽으면 과합니다.

01

현재 방식은 느리고 잘 깨집니다

스크린샷을 반복하거나 페이지를 텍스트로 바꾸고, 클라우드 브라우저를 운영하는 방식은 토큰·인프라 비용이 들고 UI 변경에도 취약하다는 것이 영상의 문제 제기입니다. [출처 1]

02

WebMCP는 ‘가능한 작업 목록’을 먼저 보여줍니다

페이지가 도구 이름·설명·입력 스키마를 등록하면 브라우저 기반 에이전트가 필요한 기능을 발견하고 호출합니다. [출처 2] [출처 10]

03

정확한 호출과 안전한 호출은 다른 문제입니다

도구를 정확히 찾더라도 프롬프트 인젝션, 과도한 권한, 민감정보 전송이 사라지는 것은 아닙니다. Chrome도 모델 내부에서 완전한 안전을 보장할 수 없다고 설명합니다. [출처 6]

영상 표현 ①

“전체 웹 트래픽의 60%는 봇과 AI 에이전트”

사람이 인터넷에서 소수가 됐다는 도입부의 강한 후킹입니다. [출처 1]

공식 확인

측정 범위는 ‘HTML 페이지 요청의 봇 vs 인간’입니다

Cloudflare Radar의 공식 정의는 HTML 응답에 대한 HTTP 요청 비중입니다. 여기에는 검색 크롤러·비AI 자동화 봇도 포함되므로 ‘AI 에이전트가 인터넷의 60%’로 바꾸면 안 됩니다. Cloudflare의 2025 분석에서도 AI 봇은 HTML 요청의 연평균 4.2%로 별도 집계됐습니다. [출처 7] [출처 8]

영상 표현 ②

“Google·Microsoft 엔지니어가 만든 W3C 웹 표준”

WebMCP가 개방형 표준 경로에 있다는 설명입니다. [출처 1]

공식 확인

정확한 표현은 ‘제안된 웹 표준’입니다

Chrome 문서는 proposed web standard라고 명시합니다. W3C Community Group의 작업 저장소가 있지만, 최종 W3C Recommendation으로 확정된 상태는 아닙니다. [출처 2] [출처 10]

“Chrome의 Gemini가 첫 지원 에이전트가 될 것”

Google이 브라우저와 에이전트를 함께 보유한다는 전망입니다. [출처 1]

공식 확인

Origin Trial은 시작됐지만 일반 지원 완료로 단정할 수 없습니다

Google I/O 2026 발표문은 Chrome 149에서 실험을 시작하고 Gemini in Chrome이 ‘곧’ 지원할 것이라고 표현했습니다. 공식 문구가 현재형으로 바뀌기 전까지는 예정 상태로 보는 편이 안전합니다. [출처 3] [출처 9]

읽는 기준: 영상은 WebMCP의 개념을 이해하기에 좋습니다. 제품 적용이나 투자 판단에는 ‘영상 촬영 당시 설명’과 ‘오늘의 공식 지원 상태’를 반드시 분리해야 합니다.
WHY CURRENT AGENTS STRUGGLE

영상이 설명한 현재의 웹 사용법은 세 가지 우회 방식입니다

웹은 사람의 눈과 손을 전제로 만들어졌기 때문에, AI 에이전트는 화면을 해석하고 사람의 행동을 흉내 내야 합니다. 아래는 영상의 설명을 정리한 것입니다. 출처 1

01

비전으로 버튼 추측

스크린샷을 모델에 보내고 버튼처럼 보이는 영역의 좌표를 클릭한 뒤 다시 화면을 확인합니다. UI가 바뀔 때마다 추측을 반복합니다.

02

페이지를 텍스트로 변환

웹페이지를 텍스트나 마크다운으로 바꾸면 읽기는 쉬워집니다. 하지만 내용 이해와 실제 주문·제출 같은 행동 완료는 다른 문제입니다.

03

헤드리스 브라우저 운영

클라우드에서 Chrome과 Playwright를 돌려 실제 브라우저를 제어합니다. 확장성은 있지만 브라우저 인프라와 유지 비용이 필요합니다.

VIDEO'S CENTRAL PROBLEM

ℹ
현재 WebMCP도 브라우저 문맥은 필요합니다. Chrome 공식 문서는 탭 또는 webview가 열려 있어야 하며, WebMCP 도구를 headless 상태에서 호출하는 기능은 지원하지 않는다고 설명합니다. 즉, 모든 브라우저 자동화를 없애는 기술은 아닙니다. [출처 2]
HOW WEBMCP WORKS

웹페이지가 선언하고, 브라우저가 중개하고, 에이전트가 호출합니다

01

페이지가 도구 등록

검색·주문·가입처럼 실행 가능한 기능의 이름, 설명, 입력 스키마를 정의합니다.

02

브라우저가 목록 유지

현재 문서가 노출한 도구와 권한 범위를 브라우저의 model context가 관리합니다.

03

에이전트가 발견

화면을 스크래핑하기보다 사용할 수 있는 도구 목록과 설명을 확인합니다.

04

필요한 도구 호출

사용자 요청에 맞는 도구와 입력값을 선택해 실행을 요청합니다.

05

페이지가 실행·반환

브라우저가 페이지 문맥에서 함수를 실행하고 결과를 에이전트에 돌려줍니다.

핵심 차이: AI가 버튼의 의미를 추측하는 것이 아니라, 웹사이트가 기능의 목적과 입력 형식을 먼저 설명합니다. 다만 호출 권한과 사용자 확인은 별도로 설계해야 합니다.

IMPERATIVE API

DECLARATIVE API

BIGGER PICTURE

FAQ

영상만 보고 가장 많이 헷갈리는 질문

WebMCP는 정식 W3C 표준인가요?
아직 아닙니다. Chrome 공식 문서는 ‘제안된 웹 표준’이라고 표현합니다. W3C Web Machine Learning Community Group의 작업 저장소가 있지만 최종 Recommendation으로 확정된 상태는 아닙니다. [출처 2] [출처 10]
지금 일반 Chrome에서 바로 사용할 수 있나요?
Chrome 149부터 Origin Trial에 참여하거나 로컬 테스트 플래그를 켜는 실험 단계입니다. Chrome Status에는 149~156 Origin Trial과 157 shipping target이 표시되지만 일정은 바뀔 수 있습니다. [출처 2] [출처 3]
영상의 ‘웹 트래픽 60%’는 AI 에이전트 비중인가요?
그렇게 해석하면 안 됩니다. Cloudflare Radar의 봇/인간 지표는 HTML 응답에 대한 HTTP 요청을 분류하며 검색 크롤러와 비AI 자동화 봇도 포함합니다. 2025년 Cloudflare 분석에서 AI 봇은 HTML 요청의 평균 4.2%로 따로 집계됐습니다. [출처 7] [출처 8]
기존 MCP 서버를 WebMCP가 대체하나요?
완전한 대체 관계로 보기 어렵습니다. WebMCP는 열린 페이지의 기능을 브라우저 기반 에이전트에 노출하는 방식이며, Chrome 문서상 브라우저 탭이나 webview 문맥이 필요합니다. 백엔드·로컬 시스템과 연결하는 기존 MCP와 적용 위치가 다릅니다. [출처 2] [출처 10]
명령형과 선언형 중 무엇을 쓰나요?
기존 HTML 폼으로 끝나는 검색·가입·문의는 선언형이 간단합니다. 동적 상태, 탐색, 여러 단계의 비즈니스 로직은 document.modelContext.registerTool()을 사용하는 명령형이 맞습니다. [출처 4] [출처 5]
프롬프트 인젝션은 해결됐나요?
해결됐다고 보기 어렵습니다. Chrome은 LLM 내부에서 안전을 완전히 보장할 수 없다고 명시하고, 신뢰할 수 없는 콘텐츠 표시, 읽기 전용 힌트, origin 제한, 사용자 확인을 권장합니다. [출처 6]
