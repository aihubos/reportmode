REPORT INTERPRETATION

Hermes 적용 시 추가한 판단

매니저 에이전트도 자연어 입력에 영향을 받으므로 보안 경계가 될 수 없습니다. 최종 권한 판단은 LLM 밖의 정책 엔진·도구 브로커·IAM이 집행해야 한다는 것이 본 보고서의 보완 판단입니다.

HERMES REFRAME

“매니저에게만 권한”에서 한 단계 더 나아가
“매니저도 권한을 직접 집행하지 않게” 해야 합니다

OWASP는 프롬프트 인젝션을 완전히 막는 단일 해법보다 최소 권한, 불신 데이터 분리, 고위험 행동의 사람 승인과 외부 통제를 권고합니다. 시스템 프롬프트 자체도 비밀 저장소나 보안 통제로 보지 말아야 합니다.34

영상의 실용적 출발점

매니저 1개에 쓰기 권한 집중

여러 서브 에이전트에 흩어진 권한을 한곳에 모아 관리 범위를 줄이는 좋은 출발점입니다.

1

2
파일 생성·외부 전송은 매니저에게 요청
3

!

권장 Hermes 운영 구조

매니저는 제안, 정책 게이트가 집행

LLM은 “무엇을 할지” 계획하지만, “할 수 있는지”는 구조화된 정책과 사람의 승인으로 판단합니다.

✓
매니저는 실행 계획·근거·변경 diff를 제출
✓
정책 게이트가 대상·범위·금액·데이터 등 규칙 검사
✓
고위험 행동은 사람이 명시 승인, 시간 초과는 거부
✓
실행기는 작업별 단기·최소 범위 자격증명만 수령
임원용 표현: “똑똑한 관리자 한 명에게 마스터키를 주는 것”보다 “관리자는 결재안을 만들고, 금고는 별도 규칙과 결재자가 여는 것”이 안전합니다.
SECURE AGENT ARCHITECTURE

Hermes는 일곱 단계의 권한 경계를 통과한 뒤에만
실제 시스템을 바꾸게 해야 합니다

자연어·문서·웹페이지는 모두 신뢰하지 않는 입력으로 취급하고, 계획과 실행을 분리하며, 실행 권한은 짧고 좁게 발급합니다. 감사 로그는 전 단계에서 병렬로 수집합니다.

01

불신 입력

사용자 메시지, 이메일, 문서, 웹, 이미지의 숨은 지시까지 데이터로 취급합니다.

02

격리·스캔

프롬프트 인젝션, 비밀 문자열, 위험 URL, 실행 명령을 탐지하고 출처를 표시합니다.

03

읽기 전용 작업자

조사·요약·비교만 수행하며 외부 전송과 쓰기 권한은 갖지 않습니다.

04

매니저·계획자

작업 목적, 대상, 변경 내용, 필요한 권한, 롤백 계획을 구조화해 제안합니다.

05

정책 게이트

도메인, 파일 경로, 금액, 데이터 등급, 시간, 사용자 권한을 코드로 검증합니다.

06

사람 승인

외부 발송·삭제·결제·배포·권한 변경은 plan/diff를 보고 명시 승인합니다.

07

제한 실행기

Docker·VM·별도 계정에서 단기 자격증명으로 실행하고 결과와 복구 지점을 남깁니다.

병렬 감사 레인

누가 요청했는지, 어떤 입력을 봤는지, 어떤 정책이 적용됐는지, 누가 승인했는지, 어떤 도구·자격증명·대상을 사용했는지, 결과와 오류를 변경 불가능한 로그로 연결합니다.

매니저 에이전트는 보안 경계가 아니라 계획과 조정 역할입니다.Policy outside the LLM
HERMES NATIVE CONTROLS

Hermes에는 이미 여러 방어층이 있지만
설정과 배치 방식이 실제 보안 수준을 결정합니다

2026년 8월 9일 확인한 공식 문서는 사용자 허용, 위험 명령 승인, 파일 쓰기 안전, 컨테이너 격리, 자격증명 필터링, 컨텍스트 스캔, 세션 격리, 입력 검증을 방어 심층의 핵심으로 설명합니다.2

01

사용자 기본 거부

게이트웨이는 플랫폼 허용목록과 DM 페어링을 지원하며, 아무 허용 규칙이 없으면 기본적으로 거부합니다.

GATEWAY_ALLOWED_USERS
금지 · 운영 환경에서 전체 사용자 허용
02

위험 명령 승인

smart, manual, off 모드를 제공하며, 응답이 없으면 기본 거부하도록 설계되어 있습니다.

approvals.mode: manual
금지 · 운영 환경의 off·--yolo
03

쓰기 경로 제한

write_file과 patch를 승인된 루트 안으로 제한하고 자격증명·환경 파일 쓰기를 차단합니다.

HERMES_WRITE_SAFE_ROOT
한계 · 터미널은 같은 OS 사용자 권한으로 우회 가능
04

컨테이너 격리

Docker 백엔드는 capability 축소, no-new-privileges, PID·tmpfs·자원 제한을 적용합니다.

terminal.backend: docker
권장 · 운영 게이트웨이는 호스트 직접 실행 금지
05

비밀정보 최소 전달

Docker는 기본적으로 호스트 환경변수를 넘기지 않으며, MCP도 명시된 환경변수만 전달하고 오류의 자격증명을 가립니다.

docker_forward_env: []
주의 · 전달한 토큰은 컨테이너 코드가 읽을 수 있음
06

웹·SSRF 통제

도메인 차단목록과 사설망·루프백·클라우드 메타데이터 접근 차단으로 내부 시스템 탐색을 줄입니다.

allow_private_urls: false
금지 · 공개 게이트웨이에서 사설 URL 허용
07

컨텍스트 인젝션 검사

AGENTS.md, .cursorrules, SOUL.md의 “이전 지시 무시”, 비밀 읽기, curl 유출, 숨은 Unicode 등을 검사합니다.

context file scanning
원칙 · 탐지는 보조층, 권한 최소화가 본체
08

Tirith 사전 실행 검사

동형이의 URL, pipe-to-shell, 터미널 인젝션을 명령 실행 전에 검사합니다. 기본값은 도구 미가용 시 통과입니다.

tirith_fail_open: false
고보안 · 미가용·시간초과도 차단, Windows는 WSL 검토

2주차
프로필·샌드박스 분리

3주차
승인·레드팀 검증

악성 문서, 숨은 지시, 시스템 프롬프트 요구, 잘못된 대상·경로·금액을 넣어 정책 게이트와 fail-closed가 작동하는지 시험합니다.

4주차
복구 훈련·확대 결정

토큰 폐기, 작업 중단, 체크포인트 복구를 실제로 수행하고 효과·오류·승인 부담을 기준으로 확대·유지·중단을 결정합니다.
