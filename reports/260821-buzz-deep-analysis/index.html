EXECUTIVE SUMMARY

Buzz의 차별점은 “대화하는 AI”가 아니라 “행동하고 책임지는 AI 동료”입니다

모든 메시지·반응·워크플로 단계·Git 이벤트를 같은 서명 이벤트 로그에 남기고, 에이전트에도 사람과 같은 독립 정체성과 채널 권한을 부여합니다. 다만 0.x 제품이며 모바일·연결 안정성·권한 승인 구조는 파일럿에서 반드시 검증해야 합니다.S2S3

Slack의 범용 협업 성숙도, Discord의 커뮤니티·음성, Telegram의 외부 도달성은 당분간 유지하고, Buzz에는 코드·조사·검토·승인처럼 에이전트 행동의 근거가 필요한 업무만 집중시키는 구성이 가장 현실적입니다.

THREE USER PERSPECTIVES

Hermes에는 실행 공간, LLM Wiki에는 원천 기록, Codex 앱에는 팀 협업 레이어입니다

세 도구는 서로 대체 관계가 아닙니다. Hermes는 범용 에이전트 런타임, LLM Wiki는 지식 자산, Codex 앱은 개인의 멀티에이전트 작업대이며, Buzz가 이들을 팀 단위의 채널·권한·감사 로그로 묶습니다.

🪽

Hermes Agent 사용자

가장 직접적인 적합성이 있습니다. 공식 문서가 3가지 연결 방식을 제공하며, 기존 Telegram·Discord·Slack gateway 옆에 Buzz를 새 플랫폼으로 추가할 수 있습니다.S9

  • Desktop preset: 설치된 hermes-acp를 자동 발견해 로컬에서 즉시 실행
  • Relay bridge: buzz-acp가 채널 멘션을 Hermes ACP 세션으로 전달
  • Native gateway: memory·skills·approvals·cron·sessions를 유지하는 가장 깊은 통합
  • 전용 Nostr 키로 채널·DM·스레드·반응·이미지·cron 전달을 운영
권고: 시험은 Desktop, 장기 운영은 Hermes native gateway. 공개 anyone 응답은 금지합니다.
📚

LLM Wiki 사용자

Buzz는 Wiki 자체라기보다 “왜 이 지식이 만들어졌는지”를 보존하는 원천 이벤트 레이어입니다. 검색·Canvas·에이전트 메모리·Git 변경을 한 흐름으로 수집할 수 있습니다.S6

  • 대화·패치·승인·출처를 같은 프로젝트 맥락으로 묶어 지식의 provenance를 강화
  • Canvas를 임시 결정문, Wiki를 장기 검증 지식으로 역할 분리
  • Hermes workflow로 주간 “지식 결정체” 초안을 만들고 사람이 승인
  • buzz mem은 에이전트 작업 메모리로 유용하나 조직 Wiki의 분류·출판을 대체하지 않음
한계: native vector RAG·지식 그래프·자동 중복 병합·공개 문서 출판은 별도 LLM Wiki 계층이 필요합니다.
⌘

Codex 맥용 앱 사용자

Codex 앱은 여러 에이전트를 병렬 감독하는 개인 command center이고, Buzz는 팀이 같은 작업을 보고 승인하는 shared room입니다.S11

  • Buzz의 Codex 지원은 codex-acp가 Codex CLI를 감싸는 방식
  • Buzz Desktop이 buzz-dev-mcp를 붙여 셸·파일 편집 도구를 제공
  • Codex 앱의 sandbox·Skills·Automations는 개인 실행 환경에 계속 유용
  • 팀 공유가 필요한 결과만 Buzz 채널·diff·workflow approval로 승격
주의: “Codex 앱 세션이 Buzz에 그대로 동기화”되는 통합은 아닙니다. CLI 로그인·설정·ACP adapter를 별도로 운영합니다.

RISKS & CONTROLS

가장 큰 위험은 제품 기능 부족보다 “에이전트에게 너무 넓은 컴퓨터 권한을 주는 것”입니다

Hermes 공식 문서는 Buzz Desktop/ACP bridge가 도구 권한 요청을 자동 승인하는 보안 특성을 경고합니다. 채널의 자유 텍스트가 셸·파일·코드 실행으로 이어질 수 있으므로 공개 bot처럼 운영하면 안 됩니다.S10

ACP 자동 승인·호스트 셸

HIGH

Hermes ACP와 Codex 도구가 terminal·file edit·execute_code를 쓸 수 있는데, unattended host가 승인 프롬프트를 자동 처리할 수 있습니다.

통제: owner-only/allowlist, 전용 OS 계정 또는 container, 읽기 전용 기본값, 제한된 repo, secret 최소화, outbound network 제한.

연결·멘션 전달 신뢰성

HIGH

공개 이슈에는 v0.5.x에서 relay reconnect 오류와 ACP mention이 queue에 도달하지 않는 silent-loss 사례가 열려 있습니다.S17S18

통제: event ID 기반 수신 확인, heartbeat canary, 실패 재처리 queue, 중요 업무는 사람이 완료 여부를 확인.

모바일·알림 전환 리스크

MEDIUM

upstream은 mobile client를 개발 중으로 표시하고 있으며, self-hosted relay 접속 관련 iOS 공개 버그도 존재합니다.S19

통제: 긴급·외부 알림은 Telegram/Slack 유지, Buzz는 desktop-first 내부 프로젝트로 한정.

암호화·감사 모델 오해

MEDIUM

Buzz는 TLS와 storage-layer 암호화를 전제로 하며 server-side 검색·eDiscovery가 가능한 구조입니다. DM E2EE는 향후 고려 사항입니다.

통제: relay operator를 신뢰 경계로 정의하고 민감정보 등급·보존·삭제·backup 정책을 별도로 수립.

0.x 업그레이드·운영 부채

MEDIUM

Relay·Postgres·Redis·S3/MinIO·TLS·key·agent host를 함께 운영하며 빠른 upstream 변경을 추적해야 합니다.

통제: upstream tag 고정, staging relay, DB/object backup, 월 1회 upgrade window, rollback runbook.

Wiki 품질 자동화의 환상

MEDIUM

대화 자동 요약만으로는 중복·오류·시점·출처 충돌이 해결되지 않습니다. Buzz search는 강하지만 Wiki의 편집 거버넌스를 대신하지 않습니다.

통제: “초안 → 근거 링크 → 사람 승인 → 게시” 4단계와 문서 소유자·유효기간을 강제.
금지선

공개 채널에서 respond_to=anyone으로 Hermes/Codex 셸 에이전트를 실행하지 말고, 사람의 Nostr 키를 에이전트와 재사용하지 마십시오. 외부 입력을 받는 bot과 내부 실행 agent는 별도 정체성·별도 host로 분리해야 합니다.

RECOMMENDATION

4주 동안 “AI 보고서·Wiki 생산 파이프라인” 하나만 검증하는 것이 가장 좋습니다

현재 사용 중인 세 메신저를 건드리지 않고, Buzz가 가장 강한 영역인 에이전트 실행·검토·변경 기록부터 증명합니다. 성공하면 Slack의 일부 기술 프로젝트 채널만 단계적으로 이동합니다.

권장 역할 분담

Telegram외부 네트워크, 긴급 알림, 개인 모바일 bot. 시스템 오브 레코드는 아님.
Slack전사 일반 협업과 non-technical 팀. 파일럿 기간에는 기본 업무 채널 유지.
Discord커뮤니티·행사·음성·화면 공유. 외부 참여자와의 실시간 공간.
BuzzAI 리서치·개발·검토·승인·배포의 내부 프로젝트 기록.
Hermesnative gateway로 조사·memory·skills·cron을 수행하는 범용 실행 agent.
Codex앱은 개인 command center, CLI+ACP는 Buzz room의 코드 실행 agent.
LLM Wiki승인된 결론·출처·버전만 장기 보관하는 지식 publishing layer.
