AI의 답변보다,
팀의 인수인계가 느려졌다.

한 직원이 AI에게 분석을 맡긴다. 다른 직원은 별도 창에서 초안을 고친다. 두 사람은 결과를 메신저로 옮기고, 결정된 내용을 다시 AI에게 설명한다. 각자의 AI는 빨라졌지만 팀은 여전히 사람이 정보를 복사하고 맥락을 전달해야 움직인다. 이 장면은 Buzz의 개발 배경을 이해하기 위한 업무 예시다.

Block의 개발자 Tyler Longwell은 Slack에 연결한 에이전트를 운영하며 “누구의 인증정보를 쓸 것인가”, “모델이나 에이전트 실행기를 바꾸면 어떻게 할 것인가”라는 문제가 생겼다고 설명한다. Buzz는 이 문제에 대해 사람·에이전트·작업·결정을 같은 공간에 두는 방식을 택했다. 개발팀이 말하는 핵심 변화는 더 똑똑한 모델이 아니라 함께 일하는 방식이다.[3]

Buzz는 AI 모델 자체가 아니라,
사람과 AI가 같은 자료를 보며 일하는 협업 공간이다.

Block의 공식 출시 발표와 2026년 7월 21일 SiliconANGLE 보도에서 제품 공개를 확인할 수 있다. 개발 주체는 Block, Inc.이고 공개 코드는 Apache 2.0으로 배포된다. Nostr라는 공개 통신 규약을 사용하지만, 공식 README는 블록체인 제품이 아니라고 명시한다. 코인 구매나 블록체인 거래가 업무 구조의 전제가 아니다.[2][14][17][18]

경영적 해석 · 도입 효과를 판단할 단위는 “AI가 몇 명인가”가 아니라 “같은 일을 반복 설명하는 시간과 검수 후 재작업이 줄었는가”다. Block의 긍정적 경험은 공급자 측 설명이며, 이 보고서는 보편적인 생산성 향상률을 제시하지 않는다.

화면에서 이해하는 업무 방식

팀원이 업무방에 요청을 남기면, 에이전트도 그 방의 구성원으로 참여한다.

Buzz의 커뮤니티는 하나의 업무 공간이고, 채널은 그 안의 업무방이다. 대화 아래에 이어지는 스레드는 특정 쟁점의 논의를 묶는다. 에이전트는 별도 개인 창에만 머무르지 않고 팀이 보는 곳에 초안·질문·작업 결과를 남길 수 있다. 공동 문서인 캔버스와 검색도 같은 공간에 연결된다.[2]

중요한 차이는 “AI의 답이 공유된다”는 것만이 아니다. 담당자가 왜 수정했는지, 무엇을 보류했는지, 어떤 자료를 근거로 판단했는지도 같은 대화에 남길 수 있다. 후속 작업자는 결과물만 받는 대신 의사결정 과정을 읽는다. 다만 검색할 자료가 실제로 그 공간에 존재하고 에이전트에게 접근 권한이 있어야 한다.

기대의 경계 · Buzz를 설치했다고 회사의 이메일·ERP·드라이브가 자동으로 연결되지는 않는다. 외부 시스템의 자료 조회·변경은 별도 도구 연결과 권한 설계가 필요한 업무다.

사람·에이전트·모델의 역할

그 방에서 일을 하는 주체와 일을 기록하는 시스템은 서로 다르다.

사람목표·자료 범위·완료 기준을 정하고 결과를 승인한다.
에이전트모델을 호출하고 허용된 도구로 조사·작성·수정한다.
AI 모델언어를 이해하고 추론·생성을 수행한다. 별도 공급 또는 연결 대상이다.
Buzz대화·신원·권한·결과와 작업 흔적을 공유 공간에 연결한다.

예를 들어 “경쟁사 동향을 정리하라”는 요청을 받으면, 에이전트가 검색 도구로 자료를 찾고 모델을 이용해 초안을 작성한다. Buzz는 그 요청과 답변이 팀에게 전달되고 기록될 공간을 제공한다. 웹 검색 권한이 없는 에이전트는 최신 자료를 자동으로 확보할 수 없고, 좋은 모델을 쓴다고 잘못된 입력 자료가 바로잡히는 것도 아니다.

공식 문서는 Goose·Codex·Claude Code 등의 실행기를 ACP라는 연결 규약으로 붙이는 구조를 설명한다. MCP는 에이전트가 파일 편집이나 셸 같은 도구를 이용하도록 잇는 규약이다. 비전공자에게는 ACP는 에이전트 연결 규격, MCP는 업무 도구 연결 규격 정도로 이해하면 충분하다.[2][12]

서비스 약관은 기본 에이전트 구성을 사용하더라도 AI 모델 접근은 사용자가 공급해야 하며, 모델 비용·API 키·에이전트 행동에 대한 책임도 사용자에게 있다고 규정한다. 따라서 “Buzz 이용료”와 “AI 사용료”는 같은 항목이 아니다.[5]

운영 제안 · 조사 담당과 최종 검증 담당을 나누고, 에이전트의 이름·소유자·허용 자료·허용 행동을 명시한다. 여러 에이전트의 의견 일치만으로 사실 확인을 대체하지 않는다.

첫 업무는 보고·조사·검토가 적합하다.

기획팀은 공개 시장 자료를 모으고, 검토자는 각 주장에 원문 링크가 붙었는지 확인한다. 교육팀은 강의 구성안을 공유하고, 자료 조사와 문장 다듬기를 다른 에이전트에게 맡긴다. 마케팅팀은 영상의 특정 장면에 수정 의견을 남긴다. 앞의 두 사례는 도입 제안이며, 마지막 장면은 공식 제품 화면에서 확인할 수 있는 미디어 댓글 기능에 대응한다.[2]

개발 업무에서 드러나는 차이

개발팀에서는 “대화가 실제 변경으로 이어졌는가”를 더 구체적으로 추적할 수 있다.

Git은 코드와 파일의 변경 이력을 관리하는 방식이다. PR은 변경안을 검토해 달라는 요청이고, CI는 변경 후 자동 검사를 실행하는 절차다. Buzz는 Git 이벤트와 저장 기능을 제공하고, 대화·변경안·검토·병합 결정을 하나의 프로젝트 흐름에 연결하려 한다. 개발자가 아닌 임원은 “누가 무엇을 바꿨고 누가 확인했는가”를 보는 창으로 이해하면 된다.[2][3][11]

독자적으로 Git 저장소를 운영하는 방향과 기존 GitHub를 유지하면서 Buzz를 협업 계층으로 쓰는 방향이 모두 문서에 나온다. 따라서 도입 초기에 코드 저장소까지 이전할 필요는 없다. 우선 기존 시스템의 변경안 링크와 검수 결과를 Buzz 대화에 연결하는 방식이 전환 위험을 줄인다.[10]

현재와 비전 구분 · Git 저장 기능과 초기 프로젝트 화면이 있다는 사실은 모든 브랜치 생성·검토·승인·배포가 완성된 단일 흐름으로 자동 실행된다는 뜻이 아니다. 전체 무인 배포를 납품된 기능처럼 평가하지 않는다.

“우리 서버”와 “우리 안에서만 처리”는 다르다.

직원 데스크톱요청·검토·승인
에이전트 실행 환경모델 호출·허용된 도구 실행
↕ 대화와 작업 결과 전달
Buzz relay · 공동 업무 기록 서버신원 확인 / 채널 접근 / 메시지 전달 / 검색·작업 기록
데이터베이스대화·이벤트·검색
파일 저장소미디어·첨부·저장 객체
별도 정보 처리 경계에이전트 → 선택한 AI 모델 제공자 · 외부 업무 도구

릴레이(relay)는 메시지와 작업 이벤트를 받아 저장하고 전달하는 서버다. 공식 구조에는 대화와 검색을 위한 PostgreSQL, 실시간 전달을 위한 Redis, 파일을 위한 S3/MinIO 저장소가 나온다. 비전공자에게 중요한 것은 기술명이 아니라 운영자·저장 위치·접근권한·백업 책임이 각각 정해져야 한다는 점이다.[2][8]

Block 호스팅형에서는 연결한 외부 AI 모델 제공자가 입력과 관련 채널 콘텐츠를 받을 수 있다.[5][6] 자가 호스팅에서도 외부 모델·도구를 선택하면 외부 전송이 발생할 수 있으나, 실제 전송 범위는 선택한 연결 구성의 시험과 계약 검토로 확인해야 한다. 공식 소개도 외부 전송을 운영자의 선택과 연결한다.[17] 모델을 내부에서 실행하면 하드웨어·운영·품질 검증을 따로 책임져야 한다. 자체 호스팅만으로 모든 데이터가 사내에 머문다고 결론 내릴 수 없다.

도해는 공식 구조를 임원용으로 단순화한 설명이다. 회사에 실제 구축한 네트워크도나 모든 통신 경로를 망라한 보안 설계도가 아니다.

권한과 신원 관리

접근 통제는 에이전트를 누구의 이름으로 일하게 할 것인지에서 시작한다.

Buzz는 사람과 에이전트에게 각각 공개키·개인키로 이루어진 신원을 부여한다. 공개키는 식별표에, 개인키는 서명 도구에 가깝다. 누군가 개인키를 가지면 그 신원으로 행동할 수 있다. 사람이 자신의 신원을 에이전트에게 그대로 빌려주기보다 에이전트의 저자 신원과 소유자의 승인을 구분하는 것이 제품 설계의 핵심이다.[3][5][7]

6주 확장안과 확대 기준

4주 기본 실험 뒤, 조직 단위 검증이 필요하면 6주안으로 확장합니다.

HTML의 4주안과 Word의 6주안은 서로 다른 제안입니다. 단일 공개자료 브리핑은 4주로 시작하고, 10~15명·업무 2종·에이전트 2~3개를 평가하려면 아래 6주안을 선택할 수 있습니다. 두 기간 모두 공급자의 권장 일정이나 성과 보장이 아닙니다.

1–2주

기준선과 실행 환경

기존 시간·오류·비용을 측정하고 허용 자료, 담당자, 모델·실행기 버전, 예산, 중지 조건을 정합니다.

3–4주

읽기에서 제한된 쓰기로

요약·분류·검토를 비교한 뒤 샘플 문서의 저위험 수정만 사람이 승인합니다.

5주

실패와 회수

기기 분실, 권한 회수, 중지, 백업 복원, 허용하지 않은 지시의 차단 여부를 확인합니다.

6주

확대·연장·중단

같은 품질의 결과를 만드는 순투입 시간과 총비용, 운영 부담을 비교합니다.

확대 결정 전에 합의할 기준

예시 목표는 품질을 유지하면서 사람의 순투입 시간을 20% 이상 줄이는 것입니다. 이는 보장 수치가 아니라 실험 전에 정할 목표입니다. 중요 오류 증가 여부, 산출물당 비용, 접근 회수·자료 반출·복구 가능성, 한국어 입력과 단말 사용성도 함께 판단합니다.

임원 질의응답

회의에서 짚어야 할 여섯 가지.

기존 메신저와 무엇이 다른가요?

사람과 AI 실행 주체가 같은 업무 맥락에서 참여하도록 설계됐습니다. 기존 제품이 AI를 지원하지 않는다는 뜻은 아닙니다. 반복 설명과 조정 부담이 줄어드는지 업무별로 비교해야 합니다.

Buzz를 쓰면 AI가 더 똑똑해지나요?

기반 모델의 능력이 자동으로 높아지지는 않습니다. 역할·자료·기억·도구·협업 방식이 바뀝니다. 기억 저장도 모델 재학습과는 다릅니다.

무료인데 왜 예산이 필요한가요?

초기 호스팅 이용료와 모델 호출비는 별개입니다. 연결·검수·운영·권한 관리에 드는 사람의 시간도 비용입니다.

자체 서버면 자료가 모두 내부에 머무르나요?

외부 모델과 도구로 보내는 자료는 별도 경로입니다. 자체 릴레이만 운영한다고 외부 처리가 없어지지는 않습니다.

코인이나 블록체인이 필요한가요?

Buzz는 서명한 이벤트를 릴레이가 기록·전달하는 구조입니다. 암호화폐 구매나 블록체인 거래가 전제가 아닙니다.

지금 무엇을 결정하면 되나요?

실험할 업무, 책임자, 허용 자료·권한, 예산 상한, 중지 조건과 종료일을 정합니다. 전사 전환은 품질·경제성·운영 증거를 얻은 후 판단합니다.

Buzz는 사람과 여러 에이전트가 같은 업무 맥락에서 작업하고, 그 과정과 결과를 함께 볼 수 있도록 설계된 공개 협업 공간이다. 실제 데스크톱·호스팅 진입 경로가 있고, 대화뿐 아니라 문서·미디어·Git 작업까지 연결하려는 범위가 분명하다. 공동 AI 업무가 많은 팀에게는 충분히 검토할 가치가 있다.[2][3][4]
